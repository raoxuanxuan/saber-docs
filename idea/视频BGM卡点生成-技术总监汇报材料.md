# 视频 BGM 卡点生成 — 技术方案汇报

## 一、需求背景

### 1.1 需求来源

老板原话：**"我们要想想比如我传个视频上来，生成一个新的 bgm 配上，卡点和内容都弄对上"**

### 1.2 需求拆解

| 要求 | 含义 | 核心技术 |
|------|------|---------|
| **卡点对上** | BGM 节拍和视频画面转场节奏同步 | 视频转场检测 + 音频节拍对齐 |
| **内容对上** | BGM 风格/情绪和视频画面内容匹配 | 多模态 AI 内容理解 + 风格化音乐生成 |

### 1.3 约束条件

- **视频时长**：v1 先支持 15 秒短视频
- **处理方式**：用户提交任务，异步处理
- **耗时要求**：总耗时控制在 ~55 秒（C 端业务可接受范围）
- **卡点精度**：150ms 容忍度（普通用户无感知差异）
- **迭代计划**：v1 做转场卡点，后续可扩展动作卡点（人物起跳、运镜变化等）

## 三、方案概览

### 3.1 Pipeline 总览

```
用户上传 15s 视频
       │
       ▼
  Step 1: 视频分析           ~5s
  ├─ 转场检测（时间戳提取）
  └─ 内容理解（风格/情绪识别）
       │
       ▼
  Step 2: Suno 并行生成       ~30-60s（主要耗时）
  └─ 3 首候选 BGM 并行生成
       │
       ▼
  Step 3: 选曲 + 对齐         ~3s
  ├─ 节拍追踪（Beat Tracking）
  ├─ 滑动窗口评分选曲
  └─ BPM 微调（Time-Stretching）
       │
       ▼
  Step 4: 合成输出            ~2s
  └─ 视频 + BGM 合并
       │
       ▼
  回调通知用户，总耗时 ~40-70s
```

### 3.2 服务架构

```
                         ┌─────────────┐
  用户上传视频 ──→ BFF ──→│  MQ (Kafka)  │
                         └──────┬──────┘
                                │
                         ┌──────▼──────┐
                         │  编排服务     │  Go
                         │  Orchestrator│
                         └──────┬──────┘
              ┌─────────────────┼─────────────────┐
              ▼                 ▼                  ▼
      ┌───────────────┐ ┌────────────┐  ┌────────────────┐
      │ 视频分析服务    │ │ Suno代理    │  │ 音频处理服务     │
      │ Python (gRPC) │ │ Go (gRPC)  │  │ Python (gRPC)  │
      └───────────────┘ └────────────┘  └────────────────┘
```

- **编排服务（Go）**：任务状态管理、步骤串联、超时控制、失败重试
- **视频分析服务（Python）**：转场检测 + LLM 内容理解
- **Suno 代理（Go）**：封装 Suno API，管理并行生成
- **音频处理服务（Python）**：Beat Tracking + 对齐评分 + Time-Stretching + ffmpeg 合成

### 3.3 各步骤技术选型

| 步骤 | 做什么 | 技术选型 | 成熟度 |
|------|--------|---------|--------|
| 转场检测 | 找视频画面切换点 | PySceneDetect（开源库） | 成熟，工业级 |
| 内容理解 | 识别视频内容和情绪 | Claude/GPT-4V 多模态 LLM | 成熟 |
| BGM 生成 | 生成匹配风格的音乐 | Suno API（已接入） | 已有 |
| 节拍追踪 | 检测音乐节拍位置 | librosa（开源库） | 成熟，学术+工业双验证 |
| 时间拉伸 | 微调 BPM 对齐 | pyrubberband（开源库） | 成熟，工业级 |
| 音视频合成 | 合并视频+音频 | ffmpeg | 行业标准 |

## 四、关键技术指标

### 4.1 卡点质量

- **对齐率目标**：>= 70%（即 5 个转场中至少 3-4 个卡上）
- **容忍度**：150ms（人耳对节拍偏移的感知阈值）
- **实现保障**：3 首候选 + 滑动窗口选最优 + Time-Stretching 微调

### 4.2 耗时分布

| 步骤 | 耗时 | 占比 | 优化空间 |
|------|------|------|---------|
| Step 1 视频分析 | ~5s | 8% | 转场检测和内容理解并行 |
| Step 2 Suno 生成 | ~30-60s | 80% | 3 路并行，耗时取决于 Suno API |
| Step 3 选曲对齐 | ~3s | 5% | 纯计算，很快 |
| Step 4 合成输出 | ~2s | 3% | -c:v copy 不重编码 |
| **总计** | **~40-70s** | | |

Step 2 是耗时瓶颈，取决于 Suno API 响应速度，非我方可控。

### 4.3 可用性保障

| 风险场景 | 兜底策略 |
|---------|---------|
| Suno 3 首全部超时 | 走预置 BGM 曲库匹配 |
| Suno 部分失败 | 允许 1-2 首成功即可继续 |
| 对齐率都很低 | 走曲库兜底方案 |
| 全局超时 3 分钟 | 标记失败，通知用户重试 |

## 五、资源评估

### 5.1 新增服务

| 服务 | 语言 | 工作量 | 说明 |
|------|------|--------|------|
| 任务编排服务 | Go | 中 | 核心编排逻辑，状态机，MQ 消费 |
| 视频分析服务 | Python | 中 | PySceneDetect + LLM 调用 |
| 音频处理服务 | Python | 中 | librosa + pyrubberband + ffmpeg |

Suno 代理服务已有，需小幅扩展支持并行生成和 prompt 模板。

### 5.2 依赖

- 对象存储（OSS）：视频/音频中间产物和最终结果存储
- 消息队列（Kafka）：任务分发
- 多模态 LLM API（Claude/GPT-4V）：内容理解

### 5.3 外部成本

| 项目 | 单次任务成本 | 说明 |
|------|------------|------|
| Suno API | 3 次生成/任务 | 并行 3 首候选 |
| 多模态 LLM | 5-6 张图/任务 | 抽帧分析 |
| 存储 | ~10MB/任务 | 视频+3首候选+最终输出 |

## 七、风险评估

| 风险 | 等级 | 影响 | 应对 |
|------|------|------|------|
| Suno BPM 控制不精确 | 中 | 对齐率下降 | 多候选 + Time-Stretch 兜底 |
| Suno API 响应慢/不稳定 | 中 | 耗时增加 | 超时机制 + 曲库兜底 |
| LLM 内容理解不准 | 低 | 风格不匹配 | 预设风格模板库做分类兜底 |
| 15s 音频 Beat Tracking 不稳定 | 低 | 节拍检测偏差 | 生成 30s 截取最优 15s |
