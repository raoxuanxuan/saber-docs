# Suno Music Advisor — 技术架构说明

## 一、定位

将用户的音乐创作意图（情绪描述 / 流派选择 / 参考歌曲）转化为 Suno AI 可直接使用的高质量 prompt。

核心价值：**让不懂音乐制作的人也能精准控制 Suno 的输出风格。**

两种使用场景：
- **在线交互**：用户通过 Skill 单首分析歌曲，实时生成 Suno prompt
- **离线批量**：基于曲库元数据 + 标签库，批量生产百万级 Suno prompt

## 三、标签库

### 定位

一个**经验验证型**的标签知识库。与 genre-database.md（音乐理论导向）不同，标签库追踪的是 **Suno 实际会响应什么** —— 有效性评分、标签交互、社区验证过的模式。

核心原则：
1. **经验优于理论** —— 标签价值 = 对 Suno 输出的影响，而非音乐理论的准确性
2. **评分制，非二元** —— 每个标签有 0.0-1.0 的有效性评分
3. **感知交互** —— 协同和冲突关系直接影响 prompt 质量
4. **来源标注** —— 每个数据点可追溯：official > tested > community > inferred

### 当前规模（2026-03-22）

| 指标 | 数量 |
|------|------|
| 标签总数 | **956**（710 genres, 55 instruments, 51 vocals, 50 moods, 39 production, 51 其他） |
| 交互关系 | **34**（14 synergy + 4 conflict + 1 redundant + 15 原有） |
| better_than | **9** 条（全部来自社区，共性：精确术语 > 泛化描述） |

数据来源：种子 105 → Phase 1 sunoprompt.com +748 → Phase 2 Reddit +103 + 26 eff 校准

### 两层架构：索引 + 详细档案

```
_suno-vocabulary.yaml（扁平索引，956 条）
    { tag, eff, src, note? }
    - Step 3.5 校验的第一入口，90% 场景够用
                │
                │ 需要 aliases / better_than / description_zh 时
                ▼
类别子文件（详细档案，如 genres/electronic.yaml）
    完整 Schema：tag, category, effectiveness, strength,
    source, aliases, description_zh, better_than, notes...
    - 子文件不存在时自动降级，仅用索引
```

### 评分体系

| 分数 | 等级 | 含义 |
|------|------|------|
| ≥ 0.9 | **strong** | Suno 稳定响应，核心词汇（~15 个） |
| 0.7-0.89 | **reliable** | 通常有效，推荐使用（~80 个） |
| 0.5-0.69 | **moderate** | 不稳定，需搭配辅助标签 |
| < 0.5 | **weak** | 可能被忽略，建议替代 |
| 0.70（默认） | — | Phase 1 批量导入，未实测（~855 个） |

### 关键发现

来自 Reddit "The Science of Suno"（145↑，含 Suno 内部权重数据）：
- **Pop 是万有引力中心** —— 所有风格都与 pop 高共现，不指定子流派会偏 pop
- **Rap 默认走 Trap** —— rap→trap 共现率 327B，要 boom bap 需显式指定
- **精确术语 > 模糊描述** —— "tape saturation" >> "warm fuzzy feeling vibe"

## 五、批量生产：质量与成本的权衡

标签库不仅服务于单首歌的在线 Skill，更要支撑**百万级曲库的离线 Suno prompt 生产**。

### 问题

| 维度 | 单首 Skill | 百万首（串行） |
|------|-----------|--------------|
| Web 搜索 | 0-5 次 | 200万-500万次 |
| LLM 推理 | 1 次对话 | 100万次 API |
| 耗时 | ~30秒 | ~347 天 |
| 成本 | 可忽略 | ~$50,000 |

### 解决方案：三层架构

```
酷狗曲库元数据（流派、情绪、乐器等，已有数据）
        +
librosa 音频分析（提取 BPM、Key，纯计算无成本）
        ↓
LLM 仅做"术语翻译"（批量 20首/调用）
  - 不搜索、不做深度分析
  - 把音乐术语转成 Suno 认的词汇
  - 如：「嘻哈 + 唢呐 + 暗黑」→「dark hip-hop, suona, aggressive」
        ↓
标签库校验（_suno-vocabulary.yaml + _interactions.yaml）
  - 纯代码逻辑，无 LLM/搜索成本
        ↓
按固定模板组装 Suno prompt
```

### 方案对比

| 方案 | 百万首成本 | 质量 | 适用 |
|------|----------|------|------|
| A. 逐首 Skill（LLM+搜索） | ~$50,000 | 最高 | 不可行 |
| **B. 曲库元数据+LLM 批量翻译** | ~$2,000-5,000 | 知名高/冷门中 | **推荐** |
| C. 纯映射表（无 LLM） | ~$0 | 低 | 仅粗筛 |

### 关键 trade-off

LLM 批量补全靠训练知识，不搜索。热门歌曲几乎无差异（仅缺 BPM/Key，librosa 补），冷门歌曲质量下降。

**标签库越完善 → 校验命中率越高 → 批量生产成本越低**。这是标签库建设的直接商业价值。

## 七、核心设计决策

### 1. 为什么要分级搜索？

| | 全搜索 | 分级搜索 |
|---|--------|---------|
| 热门歌曲 | 5 次搜索，大部分确认已知 | 2 次搜索，效率 +60% |
| 冷门歌曲 | 5 次搜索 | 3-5 次（同） |

LLM 训练数据已覆盖热门歌曲的音乐知识，搜索只需验证 BPM/Key。

### 2. 为什么要搜 Suno 社区 prompt？

音乐分析术语 ≠ Suno 有效标签：
- "唢呐" → `suona` 可用但不稳定 → 社区建议加 `Chinese double-reed`
- "talk-singing" → Suno 无此标签 → 社区用 `rhythmic spoken vocals`

### 3. 为什么用 14 维度？

精细维度（节奏型/空间感/动态）写入 Line 2-4，让 Suno 在更多维度贴近参考歌曲。

### 4. 标签库 vs Web 搜索的关系

不是替代，而是互补：
- 标签库命中 → 跳过搜索（省时省成本）
- 标签库未命中 → Web 搜索兜底
- 搜索发现新知识 → Step 6.5 回写标签库（闭环成长）

### 5. Feature Flags

| Flag | 默认 | 控制 |
|------|------|------|
| `tag_library` | true | Step 3.5/5 是否查标签库（"读"开关，"写"始终激活） |
| `triangulation` | false | Step 3.7 相似歌曲交叉验证 |

## 九、局限性

1. **Suno 标签体系不公开** — 社区经验是最佳信息源，但非官方文档
2. **Web 搜索依赖** — Tunebat 等站点可能被反爬（403），需降级策略
3. **精细维度部分靠推断** — 节奏型、空间感等搜索结果未必明确提及
4. **Suno 生成质量不可控** — 即使 prompt 完美，输出仍有随机性
5. **标签库 eff 校准不足** — 956 标签中 ~855 个处于默认 0.70，待逐步校准
