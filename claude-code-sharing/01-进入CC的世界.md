 # Claude Code 可以用的更好（上篇）：进入 CC 的世界

> 分享目标：让 CC 使用者从"会用"走向"理解"，建立对 CC 架构的直觉认知。
> 听众画像：业务研发为主，日常使用 DeepSeek/千问/Cursor/CodeBuddy，多数人用 CC 做对话式编程但没深入碰过配置体系。

---
## 1. 初步印象

### 1. CC是一个编码辅助工具

- 生成代码：打开CC终端，你跟它说："阅读XXX，帮我写XXX，要求是XXXX" 它在当前目录里生成一份代码文件。

- 同事丢过来一个报错截图："这个接口 500 了，你看看。" 你把报错信息扔给 CC，它帮你分析原因、给出修复方案。

- "这段并发代码有没有 race condition？" "帮我给这个函数写个单元测试。" CC 给你分析、给你建议。

### 2. CC 是一个通用接口

CC 的能力边界远比"写代码"大。它能调用任何命令行工具，这意味着：

```
视频编辑      → ffmpeg（"帮我把这个视频压缩到 10MB 以内"）
音频转写      → Whisper（"把这段会议录音转成文字"）
数据分析      → Python / pandas / matplotlib（"分析这份 CSV，画个趋势图"）
磁盘清理      → 查找大文件、清除缓存、docker system prune
文档转换      → pandoc（"把这个 Word 转成 Markdown"）
```

CC 创始人 Boris Cherny 说他**已经 6 个多月没写过一行 SQL**——团队在代码库中维护了一个 BigQuery Skill，所有人直接在 CC 中做分析查询。这适用于任何有 CLI、MCP 或 API 的数据库。

### 3. CC还是你的个人助理

再往前一步，你会发现它的边界比你想的还要远。

**内容创作**
你现在看到的这份分享材料，就是在 CC 里写的。我让 CC 帮我整合材料、梳理大纲、组织论点、润色文字、配图。它不是在帮我写代码，它在帮我**做内容**。

**信息收集**
早上想看看 AI 圈昨天有什么新动态。跟 CC 说一句："帮我看看 XXX上昨天的热门 AI 文章，翻译成中文摘要，存到我的笔记里。" 它自己去抓 RSS、筛选、翻译、格式化、存进 Obsidian。喝完一杯咖啡，日报就好了。

**知识沉淀**
在 X 上看到一篇很好的技术长文，发给 CC 一个链接："保存这篇文章。" 它自动抓取内容、翻译成中文、生成摘要、分类存进知识库。以前这个流程要：复制链接 → 打开阅读器 → 手动翻译 → 手动整理笔记。现在一句话搞定。

**最耐心的老师**
把不懂的问题丢给它，他会告诉你完整的解决方案；把技术文章给它，它给你全部实现

**生成可视化 HTML 演示文稿**：让 CC 解释不熟悉的代码，它做的幻灯片出人意料地好

**画 ASCII 图**：让 CC 画架构图、流程图、时序图、数据流图都能画。比起 Mermaid 或 Excalidraw，ASCII 图的优势是直接嵌在 Markdown 或终端里，零依赖，随处可读。

CC 不关心你给它的任务是不是"写代码"。它关心的是：**这个任务能不能拆成一系列工具调用？** 只要能，它就能做。代码只是它会用的工具之一。所以与其说它是编码工具，不如说——**你的终端就是你的个人助理入口。**

说到个人助理， OpenClaw 做的事情就是让 AI 当你的 7x24 个人助理，接入 Telegram、WhatsApp，随时喊它干活。听起来和 CC 完全不同？其实不然。**CC 和 OpenClaw 的能力内核是一样的——都是 LLM + 工具调用。** 它们的差异只在于：CC 的入口是终端，OpenClaw 的入口是 IM。CC 是你坐到电脑前它什么都能干；OpenClaw 是你走在路上也能发条消息让它干活。社区已经有人把 CC 封装成 OpenClaw 的形态了——说明底层能力完全够用，差的只是一个 IM 层。

## 2. 三个你每天都遇到的场景

### 场景一：改代码——"帮我加个分页接口"

你跟 CC 说了一句话："帮我给这个列表接口加上分页"。

然后你看到 CC 开始忙了——

它先用 Grep 搜了你的路由注册，找到了对应的 handler 文件。然后用 Read 读了这个 handler，发现里面调了一个 service 层的方法。它又跳过去读了 service 层，看到了数据库查询。接着它改了 handler 加上了分页参数解析，改了 service 层加上了 LIMIT/OFFSET，改了路由文件里的响应结构。最后它跑了一遍 `go build`，编译通过了。

一句话进去，三个文件改完了。

**你可能觉得：模型很聪明，它"理解"了我的项目。**

但你仔细看 CC 的输出就会发现——它不是一次性"想好"要改什么的。它是一步一步来的：先搜、再读、再改、再验证。每一步的结果都会喂回给模型，让它基于新的信息做下一个决定。

而且你注意到它用的不是 `cat` 读文件、不是 `sed` 改文件——它用的是 CC 自己的 Read、Edit、Grep 工具。这些不是花架子：Read 能控制读取范围，不会一次灌 5000 行进上下文；Edit 做的是精确的字符串替换，不是正则替换；Grep 搜出来的结果带文件路径和行号，模型一看就知道下一步去哪里。

**实际上：CC 有一套专用的工具系统，模型在一个循环里不断调用这些工具、拿结果、再决策。它能改对文件，不是因为模型"理解"了你的项目，是因为工具设计得好，让模型每一步都拿到了对的信息。**

如果你拿同样的模型，但让它通过一个只有 bash 的简陋 agent 来改代码——`cat` 截断不可预测、`sed` 遇到特殊字符就崩——效果会差很多。模型能力没变，工具变了，结果就变了。

### 场景二：中途停下来列 todo

你让 CC 做一个稍微复杂的任务："帮我把这个模块从 MySQL 迁移到 Redis 缓存，包括读写逻辑、过期策略、还有原来的降级方案"。

CC 开始做了。改了第一个文件，改了第二个，做到第三步的时候——它突然停了一下，输出了一段任务清单：

```
- [x] 1. 添加 Redis 缓存读取逻辑
- [x] 2. 修改写入路径，先写 Redis 再写 MySQL
- [ ] 3. 实现过期策略
- [ ] 4. 添加降级方案（Redis 不可用时回退 MySQL）
- [ ] 5. 更新单元测试
```

然后继续做第三步。

**你可能觉得：CC 真自觉，主动做计划管理。**

实际上，CC 有一个"问责机制"。系统会追踪模型有多少轮没有更新任务状态。如果连续几轮都在闷头干活但不回顾计划，系统会自动往对话里插一条提醒——相当于有个人在旁边拍你肩膀说"更新一下你的进度"。

为什么需要这个机制？因为大模型在长任务中有一个通病：做着做着就"忘了"自己要干什么。上下文越来越长，系统提示的影响力越来越弱，模型开始"即兴发挥"。一个 10 步的重构任务，不加约束的话，模型可能做完 1-3 步就开始走偏——重复做已完成的步骤，或者跳过关键步骤。

TodoWrite 机制就是 CC 对这个问题的解药。它不依赖模型的"自觉性"，而是在系统层面制造了问责压力。

**你每次看到 CC "主动"更新 todo，不是它天生勤快，是有机制在催它。**

### 场景三：报错后自己修

你让 CC 帮你写一个新功能。它写完了代码，然后跑了 `go build`——报错了，有个类型不匹配。

你还没来得及说什么，CC 已经在分析错误信息了。它看到了报错的文件和行号，用 Read 读了那个位置的代码，发现是传参类型搞错了，用 Edit 改了类型声明，又跑了一遍 `go build`——这次通过了。

**你可能觉得：模型能力强，能理解错误信息。**

确实，理解错误信息是模型的能力。但关键不在这里。

关键在于——**循环没有停**。

想一下你用普通的 ChatGPT / DeepSeek 对话窗口写代码的场景：模型给你一段代码，你粘贴到编辑器里，跑一下，报错了，你得把错误信息复制回来粘贴给模型，模型再给你改好的版本，你再粘贴回去试……

**你就是那个循环。**

CC 做的事情其实很简单：模型调用 Bash 工具跑了命令 → 拿到输出（包括报错）→ 输出追加到对话历史 → 模型基于新的上下文做出下一步决策。只要模型还在调用工具，循环就不停。直到模型认为任务完成了，主动停下来。

这就是为什么 CC 能"自己修 bug"——不是什么高级能力，就是 Agent 最基本的循环机制。普通聊天窗口没有这个循环，所以你得自己当循环。

再进一步想：CC 不只是"能自动重试"。它还会在循环中积累上下文——第一次报错的信息、它尝试的修复方案、修复后的新报错——这些都在 messages 列表里。每次调用模型时，它看到的是完整的"调试历史"，而不是一条孤立的错误信息。这和你在聊天窗口里粘贴一条报错是完全不同的信息密度。

**循环 + 上下文积累，这才是 CC 处理复杂任务时质量更高的根本原因。**

> **CC 团队的真实用法**：CC 创始人 Boris Cherny 分享过团队内部的 Bug 修复方式——"启用 Slack MCP，把 Slack 里的 Bug 讨论线程粘贴给 Claude，说一句 'fix'。零上下文切换。"甚至直接说"去修复失败的 CI 测试"，不用微管理具体怎么修。这就是循环机制在真实工作中的威力——你给它真实数据，循环替你完成剩下的事。

## 2. 同一个模型，为什么会有差距
 
市面上做这件事的工具很多，大致分两类：

![](images/Pasted%20image%2020260317175348.png)

CC 属于终端 Agent。

无论是IDE Agent还是终端Agent，这些工具底下跑的可以是同一个模型，比如都接入Claude Opus 4.6，但 CC 出来的代码质量、任务完成率，好像就是高一截。改代码改得更准、上下文记得更牢、复杂任务不容易跑偏。

为什么？模型一样，差距在哪？**答案不在模型上，在模型之上的东西。**

Anthropic 官方课程对 CC 的定位也印证了这一点——CC 不是简单的代码补全工具，而是一个**终端 AI Agent**，通过「工具系统」自动化文件操作、命令执行和代码分析。它能理解整个项目上下文、自主规划和执行开发任务。

**当然其他Agent也会是类似的特性，只不过工程领域实现的各有差异**。

**全局视图**

![](images/Pasted%20image%2020260317151924.png)

最底下一层，是大家都熟悉的大语言模型——DeepSeek、千问、Claude，都在这里。你用 Cursor 接 Claude，用 CodeBuddy 接 Claude，用 CC 接 Claude，这一层是一样的。

**差距不在这一层。**

CC 在模型之上叠了三层东西：

- **Agent 运行时**：这一层决定了 CC 的天花板
	- 循环怎么跑
	- 工具怎么分发
	- 上下文怎么管理
	- Prompt Caching 怎么省钱
	- Compaction 怎么让长会话不丢进度

- **工程治理层**：通过 CLAUDE.md、Rules、Skills、Hooks 去教 CC 怎么在你的项目里做事
	- 哪些文件不能碰
	- 提交前必须过什么检查
	- 遇到特定场景用什么工作流
	
- **你看到的交互界面**：你每天打交道的那些行为

## 小结 

三个场景——改代码、列 todo、自修 bug——背后都是同一套 Agent 运行时在驱动。 这还只是水面上我们能看到的部分。
