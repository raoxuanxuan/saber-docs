### 1.1 上下文构成
200K的上下文用的战战兢兢：
![](images/Pasted%20image%2020260313173034.png)
1M的上下文用的肆无忌惮：
![](images/Pasted%20image%2020260323135540.png)
![](images/Pasted%20image%2020260313161556.png)

一个典型 MCP Server（如 GitHub）包含 20-30 个工具定义，每个约 200 tokens，合计 4,000-6,000 tokens。接 5 个 Server，光这部分固定开销就到了 25,000 tokens（12.5%）。

![](images/Pasted%20image%2020260313161726.png)

### 1.2 上下文加载的心智模型

```
始终常驻    → CLAUDE.md：项目契约 / 构建命令 / 禁止事项
按路径加载  → rules：语言 / 目录 / 文件类型特定规则
按需加载    → Skills：工作流 / 领域知识
隔离加载    → Subagents：大量探索 / 并行研究
不进上下文  → Hooks：确定性脚本 / 审计 / 阻断
```

![](images/Pasted%20image%2020260313164733.png)

**各层加载细节：**

1. **CLAUDE.md** — 始终常驻，每次会话都在上下文里
2. **Rules** — 可按路径加载，需要主动配置 globs：
   ```yaml
   ---
   globs: "**/*.go"
   ---
   # Go 特定规则（只在涉及 .go 文件时加载）
   ```
3. **Skill** — 正文按需加载，但所有 skill 的 description 始终在上下文里（60+ 行的列表）：
   - **始终占用**：每个 skill 的 name + description（约 1-2 行）
   - **按需加载**：skill 正文（调用 Skill 工具后注入当前会话）
   - **注意**：注入后正文留在当前会话，持续占用直到被 compaction

**理解Frontmatter**
Frontmatter 就是文件顶部被两行包裹的元数据

```yaml
---
name: go-reviewer
description: Expert Go code reviewer...
model: sonnet
tools: ["Read", "Grep", "Glob", "Bash"]
---

（下面才是正文）
```

CC 对每个 agent 的加载分两个阶段：

- **阶段 1：始终加载到主会话（固定开销）** — 只加载 frontmatter 中的 description，拼进 Agent 工具定义的描述文本，格式为 `- {name}: {description} (Tools: {tools})`
- **阶段 2：调用时加载到子进程** — 通过 Agent 工具实际调用时，frontmatter 以下的 markdown 正文作为子进程的系统提示，**不占主会话上下文**

![](images/Pasted%20image%2020260313163639.png)

### 1.3 Compaction 上下文压缩

![](images/Pasted%20image%2020260323145016.png)
压缩流程：
- 上下文快满了
- CC 开一个 fork 调用，把完整对话历史喂给模型加一句 "Summarize this conversation"（命中缓存，成本不高）
- 原来几十轮对话被替换成一段 ~20k tokens 的摘要，System + Tools 还在，腾出空间继续新的轮次。


除了写 Compact Instructions，还有一种更主动的方案：在开新会话前，先让 Claude 写一份 **HANDOFF.md**，把当前进度、尝试过什么、哪些走通了、哪些是死路、下一步该做什么写清楚。下一个 Claude 实例只读这个文件就能接着做，不依赖压缩算法的摘要质量。

---
### 1.4 上下文管理最佳实践

1. CLAUDE.md 保持短、硬、可执行，定了别频繁改——每次保存都会让后续缓存断裂
2. 稳定内容放 CLAUDE.md，易变内容口头说——临时调试指令别写进去
3. 把大型参考文档拆到 Skills 的 supporting files，不要塞进 SKILL.md 正文
4. 使用 .claude/rules/ 做路径/语言规则，不让根 CLAUDE.md 承担所有差异 
5. 给 rules 加 globs——让 golang/pitfalls.md 只在处理 .go 文件时加载
6. 精简 agent description——把 example 从 description 移到正文
7. 审视 skill 数量——60+ 个 skill 的 description 列表本身就占 2-3K
8. 长会话主动用 /context 观察消耗，不要等系统自动压缩后再补救
9. 任务切换优先 /clear，同一任务进入新阶段用 /compact
10. 把 Compact Instructions 写进 CLAUDE.md——压缩后必须保留什么由你控制，不要算法猜测
11. 会话中途不要切换模型——Prompt 缓存是模型唯一的，切换会重建缓存反而更贵，确需切换用Subagent

## 3. 循环调度（Agentic Loop）

CC 的本质不是"一次性生成答案"，而是一个这样的模式：**Think → Act → Observe** 不断循环。
这个循环让 Claude 从"回答问题的模型"变成"解决问题的代理"。

### 3.1 核心循环

![](images/Pasted%20image%2020260318233637.png)

最简单的伪代码示例：

```python
while True:
    response = claude_api.call(system + tools + messages)

    has_tool_use = False
    for block in response.content:
        if block.type == "text":
            stream_to_user(block.text)
        elif block.type == "tool_use":
            has_tool_use = True
            result = execute_tool(block.name, block.input)
            messages.append(tool_use_block)
            messages.append(tool_result_block)

    if not has_tool_use:
        break  # 模型主动停止，等待用户下一条消息
```

**关键理解**：模型自己决定什么时候停。

CC 不会在固定轮次后强制停止。一个复杂任务可能跑几十轮工具调用，只要模型判断任务未完成，循环就会继续。

### 3.2 停止条件

循环不会无限运行，有多种终止机制：

| 条件 | 触发方式 | 结果 |
|------|----------|------|
| 自然停止 | 模型响应中只有 text，没有 tool_use | 任务完成，等待用户 |
| 上下文满 | 接近 token 上限 | 触发 compaction，压缩后继续（不是真停） |
| 用户中断 | Esc / Ctrl+C | 优雅中断，可以在下一轮继续对话 |
| API 错误 | 速率限制、网络超时 | CC 自动重试，带指数退避 |

```
正常流程：
用户消息 → 工具调用 × N → 文本响应 → 停止等待

被中断：
用户消息 → 工具调用 × 3 → [用户 Esc] → 中断 → 用户可以说"继续"或换个方向

上下文满：
用户消息 → 工具调用 × 50 → 上下文接近上限 → 自动 compaction → 压缩历史 → 继续循环
```

### 3.3 流式响应与并行工具调用

CC 使用流式 API，模型的输出是逐 token 流出的：

```
模型开始生成
    │
    ├─ text tokens 逐个流出 → 实时显示给用户（打字机效果）
    │
    ├─ 遇到 tool_use block → 等待 block 完整（需要完整的参数 JSON）
    │
    ├─ 一个响应中有多个 tool_use？
    │   ├─ 无依赖关系 → 并行执行（同时跑）
    │   └─ 有依赖关系 → 模型会分多轮响应串行调用
    │
    └─ 所有 tool_result 收集完毕 → 下一轮 API 调用
```

并行工具调用是 CC 效率的关键优化之一。比如模型想同时读 3 个文件：

```
串行：Read(a.go) → 等结果 → Read(b.go) → 等结果 → Read(c.go) → 等结果
总时间 ≈ 3 × 单次延迟

并行： Read(a.go) ─┐
      Read(b.go) ─┼─→ 同时执行 → 一次性返回所有结果
      Read(c.go) ─┘
总时间 ≈ 1 × 单次延迟
```

模型是否并行调用，取决于它对工具间依赖关系的判断 。这不是 CC 的调度逻辑，而是模型的推理能力。

### 3.4 子代理调度

当模型调用 `Agent` 工具时，CC 会 fork 出一个独立的子循环

![](images/Pasted%20image%2020260323150950.png)


多个子代理可以**并行调度**，这是处理复杂任务的核心模式：

```
主循环发起 3 个并行子代理：
┌─ Agent 1: 分析认证模块安全性  ──→ 返回安全报告
├─ Agent 2: 检查缓存层性能      ──→ 返回性能分析
└─ Agent 3: 审查数据库查询      ──→ 返回优化建议

3 个 tool_result 同时回到主循环 → 模型综合分析 → 给出整体建议
```

### 3.5 Hooks：循环之外的确定性层

Hooks 不在 Agentic Loop 内部，而是挂在循环的**边缘**，在特定事件发生时触发：

![](images/Pasted%20image%2020260323152108.png)

Hook 的关键特性：
- **确定性** — 是写死的 shell 脚本，不是模型决策，100% 会执行
- **可阻断** — PreToolUse Hook 返回非零退出码，工具调用被拒绝
- **零上下文** — Hook 脚本的执行完全在上下文之外，不消耗 tokens
- **审计友好** — 可以用 Hook 记录所有工具调用日志，不影响模型行为

典型用途：

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "command": "eslint --fix $CLAUDE_FILE_PATH"
      }
    ],
    "PreToolUse": [
      {
        "matcher": "Bash",
        "command": "echo $CLAUDE_TOOL_INPUT | check-dangerous-commands.sh"
      }
    ]
  }
}
```

### 3.6 循环调度最佳实践

- **相信模型的规划能力** — 不需要手动指示"先读文件再修改"，模型会自己编排步骤
- **复杂任务先进 Plan Mode** — 让模型规划完整方案，确认后再执行，避免做到一半发现方向错
- **善用 Esc 中断** — 发现模型在错误方向上连续跑了好几轮，及时中断比等它跑完更高效
- **独立任务用并行子代理** — 多个不相关的分析/搜索任务，让 CC 同时派出多个子代理
- **观察循环轮次** — 如果一个任务跑了 20+ 轮还没收敛，通常说明需要拆解任务或补充上下文
- **用 Hooks 做确定性保障** — 代码格式化、安全检查这类确定性操作，用 Hook 比靠模型"记住"更可靠

## 4. Prompt 缓存

![](images/Pasted%20image%2020260323153500.png)


每次你和 CC 交互，CC 都要向 API 发一个完整请求。缓存机制是**前缀匹配**——从头开始，连续相同的部分命中缓存，遇到第一个不同的地方就断开。

```
请求 1: [System Prompt][Tool Defs][CLAUDE.md][历史 A]
请求 2: [System Prompt][Tool Defs][CLAUDE.md][历史 A][新消息]
                                                      ↑ 只有这部分是新的
```

所以 CC 把最稳定的内容放最前面，最易变的内容放最后面，就是为了最大化前缀缓存命中率，这也解释了为什么顺序很重要。

**实际效果**：
- 不用缓存：每轮处理 ~44K tokens
- 用缓存后：每轮只处理新增的几百~几千 tokens
- System Prompt (5.6K) + Tool Definitions (9.8K) 这 15K tokens 虽然是固定开销，但因为始终命中缓存，实际处理成本几乎为零

其他能体现缓存设计的地方：

**1. Plan Mode 为什么不切换工具集**：
直觉上 Plan Mode 应该切换成只读工具集（去掉 Write、Edit），但 CC 没有这么做。为什么？

```
切换工具集 = 改了 prompt 第 2 层 = 缓存断裂 = 代价大
加个工具   = 工具集始终不变      = 缓存完好  = 零代价
```

实际实现：`EnterPlanMode` 是模型可以自己调用的工具，工具集始终不变。Plan Mode 的"只读"不是通过限制工具实现的，而是通过对话中的指令约束——**用行为约束替代能力约束，换来缓存稳定性**。


**2. Deferred Loading**
CC 有数十个 MCP 工具，每次请求全量包含会很贵，但中途移除会破坏缓存。解决方案：发送轻量级 stub（只有工具名，标记 `defer_loading: true`），模型通过 `ToolSearch` 工具"发现"它们，完整的工具 schema 只在模型选择后才加载，缓存前缀保持稳定。


### 对用户的实操指导

| 做 | 不做 | 原因 |
|----|------|------|
| CLAUDE.md 定了就别动 | 频繁修改 CLAUDE.md | 每次保存都让后续缓存断裂 |
| 临时指令口头说 | 临时调试命令写进 CLAUDE.md | 避免污染稳定前缀 |
| rules 用 globs 按需加载 | 所有 rules 无条件加载 | 缓存前缀更短更稳定 |
| 需要切模型时用 Subagent | 会话中途直接切模型 | Opus 切 Haiku 要重建缓存，反而更贵 |
| 保持工具集不变 | 会话中途增删工具 | 工具定义变化导致缓存断裂 |
| 静态 Prompt 不放动态内容 | CLAUDE.md 里写当前日期/时间戳 | 每次会话内容都不同，缓存永远命中不了 |
| 保持工具定义顺序稳定 | 非确定性地打乱工具顺序 | 顺序变了 = 前缀变了 = 缓存断裂 |

## 5. 工具调用

工具系统是 CC Agentic 能力的基础，没有工具，Claude 只是一个聊天机器人；有了工具，它能读文件、改代码、跑命令、查数据库。

### 5.1 工具分类

```
内置工具      → Read, Write, Edit, Bash, Grep, Glob, Agent...
               CC 源码里写死的 JSON Schema，始终占 System Tools 的位置

MCP 工具      → 外部 Server 提供的工具（Playwright, GitHub, MySQL...）
               通过 MCP 协议动态发现，每个工具定义 ~200 tokens

Deferred 工具 → MCP 工具的轻量 stub（只有名字，没有完整 schema）
               模型通过 ToolSearch 按需加载完整定义
```

三类工具的上下文开销对比：

| 类型 | 定义开销 | 加载时机 | 缓存影响 |
|------|----------|----------|----------|
| 内置工具 | ~9.8K（固定） | 始终在 | 始终命中缓存，实际代价≈0 |
| MCP 工具（全量） | 每个~200 tokens | 连接 Server 时加载 | 增加前缀长度，但稳定 |
| Deferred 工具 | 每个~10 tokens（仅名字） | stub 始终在，schema 按需 | 前缀极短，缓存友好 |

### 5.2 工具调用流程

一次工具调用的完整生命周期：

```
模型生成 tool_use block（含工具名 + 参数 JSON）
    │
    ▼
CC 拦截，进入权限检查
    │
    ├─ allowedTools 匹配  → 直接执行
    ├─ denyTools 匹配     → 拒绝，错误信息返回模型
    └─ 未匹配             → 弹窗询问用户
                              ├─ 用户批准 → 执行
                              └─ 用户拒绝 → 拒绝信息返回模型
    │
    ▼
CC 执行工具，拿到结果
    │
    ▼
tool_result 追加到对话历史
    │
    ▼
带着新的历史再次调用 API → 模型继续思考
```

关键细节：

1. **tool_use 和 tool_result 是配对的** — API 协议的硬性要求，每个 tool_use 必须跟一个 tool_result，缺了会报错
2. **一次响应可以包含多个 tool_use** — 模型判断多个工具调用之间没有依赖时，会在同一轮响应中并行发起
3. **工具结果永久留在对话历史** — 直到 compaction 才会被压缩，这是上下文膨胀的主要来源

### 5.3 权限模型

CC 在模型和操作系统之间加了一层权限网关，这是它与 "裸跑脚本" 的本质区别：

```
┌─────────┐     ┌──────────┐     ┌──────────┐
│  模型    │ ──→ │ 权限网关  │ ──→ │ 操作系统  │
│ (想做)   │     │ (能不能做) │     │ (真的做)  │
└─────────┘     └──────────┘     └──────────┘
```

权限配置在 `settings.json` 中：

```json
{
  "permissions": {
    "allow": [
      "Read",
      "Glob",
      "Grep",
      "Bash(npm test:*)",
      "Bash(go build:*)"
    ],
    "deny": [
      "Bash(rm -rf:*)"
    ]
  }
}
```

支持通配符匹配：`Bash(npm test:*)` 表示所有以 `npm test` 开头的命令自动放行。逐步把你信任的操作加入白名单，是提高效率的关键 —— 每次弹窗确认都是一次人工中断。

### 5.4 工具结果的上下文代价

每次工具调用的结果都会写入对话历史，这是有代价的：

```
Read 一个 500 行文件      → ~2,000 tokens（留在历史里直到 compaction）
Bash 输出一段构建日志     → ~500-2,000 tokens
Grep 搜索返回匹配结果     → ~200-1,000 tokens
Agent 子代理返回总结       → ~500-3,000 tokens
```

10 轮工具调用下来，光结果就可能吃掉 10K-20K tokens。这就是为什么上下文管理和工具调用是紧密关联的 —— **工具用得越多，上下文消耗越快**。

**对比两种搜索策略的上下文开销：**

```
策略 A：主会话直接搜索
  Grep("findUser")        → +500 tokens（结果留在主会话）
  Read(file1.go)          → +2,000 tokens
  Read(file2.go)          → +2,000 tokens
  Read(file3.go)          → +2,000 tokens
  合计：+6,500 tokens 永久占用主会话

策略 B：子代理搜索
  Agent("找到 findUser 的实现位置和关键逻辑")
  → 子代理内部：Grep + Read × 3（不占主会话）
  → 返回一段 500 tokens 的总结
  合计：+500 tokens 占用主会话
```

### 5.5 工具调用最佳实践

- **渐进式放开权限** — 先用默认模式观察 CC 会调用哪些工具，确认安全后加入 allowedTools
- **Read 时用 offset + limit** — 精确读取需要的部分，避免一次读入整个大文件
- **Grep 先定位再精读** — 用 `files_with_matches` 找文件路径，再有针对性地 Read
- **探索性搜索用子代理** — 大范围 Grep/Read 的结果在子进程消化，只有结论回到主会话
- **关注 /context 中的 Messages 占比** — 如果 Messages 增长很快，说明工具结果在快速积累
