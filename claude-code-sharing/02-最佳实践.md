# Claude Code 可以用的更好（中篇）：最佳实践

> 这不是一份功能清单，而是按"对你工作方式冲击力最大"排序的实践指南。
> 前 8 条可能会改变你使用 CC 的姿势，后面的让你更高效。

---
## 开始之前：建立一些感性认知
### 1. 模型选择——杀鸡不要用牛刀

CC 支持在对话中选择模型（`/model`），但很多人要么永远都是Opus，要么永远都是Sonnet，从不切换。
> 成本差距：Opus 大约是 Haiku 的 50-100 倍。让 Explore agent 跑 Opus 扫文件纯粹浪费钱。

![](images/Pasted%20image%2020260317201834.png)
（当然，钞能力也能解决问题，200刀/月的pro max会员可以一直用opus4.6）

**注意**：并不是说需要在一个会话中频繁切模型，而是说要根据具体的任务一开始就选择合适的模型。因为在同一个会话中途切模型会导致 Prompt Cache 重建，反而变贵，这一点后面会讲

### 2. 给自己装一个仪表盘

大部分人用 CC 时，底部状态栏是默认的，甚至没注意过它。但这个状态栏可以高度定制，而且定制后你会发现它改变了你的使用习惯。

**推荐至少显示这几项：**

![](images/Pasted%20image%2020260317103709.png)
- **当前模型**——确认你跑的是 Opus 还是 Sonnet，不同模型能力差很多
- **Git 分支**——确认你在正确的分支上，避免改错分支
- **Token 用量进度条**——这是最关键的，随时知道上下文还剩多少空间

**为什么 token 进度条是必备的？**

因为上下文消耗是不可见的。你觉得"才聊了几轮"，但 CC 读了 10 个文件、跑了 5 条命令，每个结果都在 messages 里，token 可能已经用了 60%。没有进度条，你完全不知道。

有了它，你就能做到：
- 看到超过 50%——考虑是否该 `/compact`
- 看到超过 60%——准备写 HANDOFF 开新对话
- 看到接近 80%——立刻行动，不然等自动压缩效果更差

它就像开车时的油量表——你不会等到车抛锚了才想起来看油量。

## 第一梯队：改变你使用姿势的 10 条

### 1.  从 /init 开始

```bash
# 在项目根目录运行
claude /init
```

CC 会扫描你的项目结构，自动生成一份 CLAUDE.md，包含：

- 项目概述
- 技术栈
- 构建和测试命令
- 目录结构说明
- 代码风格约定

/init 初始化，这是投入产出比最高的一步，很多人用 CC 大半年了，项目里没有 CLAUDE.md。这意味着 CC 每次启动都是一张白纸——不知道你的项目用什么语言、什么框架、怎么构建、有什么约定。

**为什么这一步很重要？**

CLAUDE.md 是每次对话都会自动加载的"项目契约"。有了它，CC 在第一轮对话就知道：

- `go build ./...` 是你的构建命令，不用猜
- 你用 gRPC 不用 REST，不会生成错误的代码风格
- 测试用 `go test -v ./...`，不会去找 pytest
- 你的项目有特定的目录约定，新文件应该放在哪里

**但 `/init` 只能搭架子，灵魂得你来填。**

它能发现构建命令、测试指令、目录结构、技术栈——但发现不了业务规范（"先提交工作流再执行 DB 事务"）、团队约定（分支命名、错误码规范）、架构决策（"为什么用策略模式"）和踩坑经验（闭包变量捕获陷阱）。

```
CLAUDE.md 质量 = /init 搭架子 + 手动填灵魂
```

**最佳实践：**

```
✅ 从 /init 生成的基础开始
✅ 踩坑后、做完架构决策后，主动把经验写进 CLAUDE.md
✅ CC 犯了错？纠正后加一句"更新 CLAUDE.md 以免再犯"——让教训自动沉淀
✅ 只在发现自己重复告诉 CC 同一件事时才添加规则
✅ 保持简洁——Anthropic 官方自己的 CLAUDE.md 只有约 2.5K tokens
❌ 一开始就写 500 行的 CLAUDE.md
❌ 把临时调试指令写进去（口头说就行）
```

> 已经有精心维护的 CLAUDE.md？不需要定期 `/init`。多次执行 `/init` 不会覆盖，只会建议改进，由你决定是否采纳。

### 2. 上下文像牛奶 —— 越新鲜越好

CC 在新对话开始时表现最好。这不是抽卡炼丹的玄学，而是随着对话越来越长，messages 列表越来越大，几个问题同时出现：

- **系统提示的影响力被稀释**：CLAUDE.md 里的规则在 5K tokens 的对话里很显眼，在 100K tokens 的对话里就被淹没了
- **早期的错误尝试还在上下文里**：你让它改了三次的代码，三个版本都在 messages 里，模型可能引用错误的版本
- **注意力分散**：模型需要处理的信息越多，遗漏关键细节的概率越高

**最佳实践：**

```
✅ 每个新话题 → 开新对话（/clear）
✅ 感觉 CC 开始"犯糊涂" → 果断开新对话
✅ 一个任务的不同阶段 → 提交代码后开新对话
❌ 一个会话从早聊到晚
❌ 在同一个会话里切换完全不同的任务
```

有了前面的 token 进度条，你可以量化这个判断：不再是"感觉变笨了"，而是"进度条超过 60% 了，该开新对话了"。当然，很多人不愿意开新对话，是因为怕"丢失进度"。下一条就解决这个问题。

---

### 3. HANDOFF 文档法——对话可以断，进度不能丢

你不愿意开新对话，是因为 CC 在当前对话里积累了大量上下文：它读过哪些文件、试过什么方案、哪些路走不通。开新对话，这些全丢了。

HANDOFF 文档法解决的就是这个问题：**在关闭对话前，让 CC 把脑子里的东西写下来。**

```
你："在关闭对话之前，请写一份 HANDOFF.md，包括：
    1. 当前目标是什么
    2. 已经完成了什么
    3. 什么方案试过了是有效的
    4. 什么方案试过了走不通
    5. 下一步应该做什么"
```

CC 会生成一份结构化的交接文档，保存在项目目录里。

下一个对话，你只需要：

```
你："读一下 HANDOFF.md，继续之前的工作"
```

新的 CC 实例拿到了一份精炼的上下文摘要，比在 100K tokens 的长对话里翻找历史要高效得多。

**这比 `/compact` 自动压缩更好**，因为：
- `/compact` 是算法摘要，可能丢掉你觉得重要的东西
- HANDOFF 是你审查过的摘要，重点由你控制
- HANDOFF 存在文件里，跨会话、跨天、甚至跨人都能用

**进阶用法1**：在 CLAUDE.md 里加一条规则——"当上下文超过 60% 时，主动提醒我写 HANDOFF"。
**进阶用法2**：配合Hook机制，结束会话时自动写HANDOFF.md

### 4. 学会挑战 CC —— 它很抗压

CC 创始人 Boris Cherny 分享过团队内部的几个 Prompting 技巧，比"写好需求"更进一步，**挑战CC或者让CC挑战你**。

**技巧 a：让 CC 当你的审查者**

```
"Grill me on these changes and don't make a PR until I pass your test."
（严格审查我的改动，在我通过你的测试之前不要创建 PR。）
```

角色反转：不是你审查 CC 的代码，而是 CC 审查你的改动。它会找出你没想到的边界条件和潜在问题。

**技巧 b：让 CC 证明它的方案有效**

```
"Prove to me this works."
（证明给我看这能工作。）
```

CC 会主动对比 main 和 feature 分支的行为差异，跑测试验证，不再只是"生成看起来正确的代码"。

**技巧 c：推翻平庸方案**

```
"Knowing everything you know now, scrap this and implement the elegant solution."
（基于你现在知道的一切，推翻这个方案，实现一个优雅的解决方案。）
```

CC 在修复过程中积累了大量上下文——哪些路走得通、哪些有坑。让它利用这些信息重新设计，而不是在平庸方案上打补丁。

**技巧 d：写详细规格说明**

在把工作交给 CC 之前，减少歧义。你越具体，输出越好——这不是 CC 特有的规律，但在 Agent 模式下效果放大了，因为模型会基于你的规格做一系列连锁决策，模糊的输入会被逐步放大。

### 5. Plan 模式——让 CC 先想清楚再动手

按 `Shift+Tab` 进入 Plan 模式，Plan 模式下，CC 会做这些事：
- 分析你的需求
- 读取相关文件
- 提出实现方案
- 列出步骤和风险
- **但不会修改任何文件**

你审查完方案，觉得 OK，再让它执行。

Plan Mode 的核心是把探索和执行拆开，探索阶段不动文件，确认方案后再执行：
- 探索阶段以只读操作为主
- Claude 可以先澄清目标和边界，再提交具体方案
- 执行成本在计划确认之后才发生

**什么时候该用 Plan 模式？**

```
✅ 不确定实现方案时——让 CC 先调研再动手
✅ 改动涉及多个文件时——先看全局再改局部
✅ 你想理解现有代码时——让 CC 以只读模式分析
❌ 简单的、你已经知道怎么做的改动——直接让它做
```
**进阶玩法**：开一个 Claude 写计划，再开一个 Codex 以"高级工程师"身份审这个计划。
###  6. Plan模式再进一步： 拆问题，不要一步到位

这可能是最重要的一条。

很多人用 CC 的方式是：写一段很长的 prompt，描述完整的需求，然后按回车，祈祷。

```
❌ "帮我写一个完整的用户鉴权系统，包括注册、登录、JWT 生成、
    刷新 Token、权限校验中间件、密码加密、邮箱验证、限流"
```

这不是 CC 的问题，是任何 Agent 都扛不住的要求。模型的上下文有限，注意力也有限，一个 prompt 塞太多东西，它会在中间某个环节丢失细节。

**正确的方式是拆步骤：**

```
✅ 第一轮："先帮我设计用户表结构和注册接口"
   → 审查，确认，提交

✅ 第二轮："现在加登录接口和 JWT 生成"
   → 审查，确认，提交

✅ 第三轮："加 Token 刷新和权限中间件"
   → 审查，确认，提交
```

每一轮 CC 都在一个干净的、聚焦的上下文里工作。你审查过的代码已经提交了，下一轮它读到的是经过你确认的代码，不是它自己上一轮的"草稿"。

这和软件工程里拆 Task 是一个道理——最好的工程师不是一次写完一个系统的人，是知道怎么把系统拆成一个个可验证的小步骤的人。CC 只是让这个过程更快了，但拆解的能力还是得你来。

**经验法则**：如果你的 prompt 超过 5 行，考虑拆成多步。

### 7. Plan模型更进一步：TDD 闭环——给 CC 一个靶子

大部分人让 CC 写代码的方式是：描述需求 → CC 生成代码 → 你看一眼 → 觉得差不多 → 用了。

问题在于"觉得差不多"这一步太主观了。CC 生成的代码可能编译通过、看起来合理，但边界条件没处理、错误路径没覆盖。你不可能每次都逐行审查。

**TDD 的思路是反过来——先定义"什么叫对了"，再让 CC 去实现：**

```
第一步：先写测试（RED）
  "帮我写 GetUserByID 的单元测试，覆盖以下场景：
   - 正常查询返回用户
   - ID 不存在返回 nil + 特定错误
   - 数据库连接失败返回错误"

第二步：确认测试失败
  跑一遍测试，确认全红——证明测试是有效的，不是 return true 的假测试

第三步：提交测试

第四步：让 CC 写实现（GREEN）
  "现在写 GetUserByID 让这些测试通过"

第五步：测试全绿，提交
```

为什么这样效果更好？

- **CC 有了明确的目标**——不是模糊的"写一个函数"，而是"让这 3 个测试通过"
- **验证是自动的**——不靠你肉眼看，靠测试跑
- **边界条件被强制覆盖**——因为你在测试里写了
- **你只需要审查测试**——测试比实现短得多，审查成本低

先写测试再提交还有一个好处：如果 CC 后面写的实现不满意，你可以直接 `git checkout` 回到测试提交点，换个 prompt 重新让它实现。测试还在，靶子还在。

**Plan 模式 + 拆问题 + TDD 的组合拳：**

```
第一步：Plan 模式，让 CC 分析需求，输出实现方案
第二步：你审查方案，确认方向
第三步：拆成小步骤
第四步：每一步 TDD——先写测试，再实现
```

这个工作流听起来慢，但实际上比"一个大 prompt 赌运气"快得多——因为你几乎不需要返工。

## 第二梯队：让你更高效的日常习惯

### 1. 终端别名 —— 少敲点键盘

在 `~/.zshrc` 中加几行，每天省几十次敲击：

```bash
alias c='claude'           # 最常用
alias cc='claude --continue' # 继续上一个会话
```

### 2. 语音输入 —— 逼格拉满

语音输入比打字快得多，尤其适合描述需求、解释上下文。

推荐工具（macOS）：启动听写
体验拉满，即使转写有错误，CC 也足够聪明来理解你的意图。你可以用耳机小声说话——声音小到别人听不见，但足够让麦克风捕捉到。

### 3. 给CC真实数据 —— 拒绝二次加工

传统的 Bug 修复流程：你用语言描述 Bug → CC 猜错几次 → 改几次 → 最终修好。中间浪费的上下文空间是巨大的。

**更快的做法：给 CC 真实的错误信息，而不是你的二手描述。**

```
❌ "登录接口有问题，用户反馈说登不上去，我怀疑是XX错了，帮我查一下"

✅ [ 粘贴完整的错误日志 / Bug单里的case / 涉及的代码仓库 ]
   "fix"
```

CC 非常擅长从大量日志中精准定位问题。你的描述是经过过滤的，可能丢掉了关键线索；原始数据不会。

几个实用场景：
- **线上 Bug**：粘贴错误日志 + 堆栈信息，比你口述"好像是 token 过期了"精准得多
- **用户反馈**：直接粘贴原始对话，让 CC 自己判断问题在哪

### 4. 多种验证方式——不要只信 CC 说"完成了"

CC 说"已完成修改"不等于真的完成了。建立多层验证：

```
验证手段（由轻到重）：
1. 让 CC 自己跑测试             ← 最基本的
2. 在 CC 界面里直接看代码       ← 快速扫一眼
3. Git diff 看变更              ← 确认改了什么、没改什么
4. Draft PR 审查                ← 完整的 code review 视角
5. 让 CC 自我检查               ← "检查你刚才的每一个改动，
                                    列一个表格说明你验证了什么"
```

不同场景用不同级别：日常小改动用 1+2，重要功能用 1+3+4，关键业务代码全上。

**更轻量的做法：在 prompt 里直接内置验证条件。**

不一定每次都要写测试文件。对于轻量级任务，直接在 prompt 里给出验证标准：

```
❌ "写一个邮箱验证函数"

✅ "写一个邮箱验证函数。用这些案例测试：
    hello@gmail.com → 通过
    hello@ → 失败
    @domain.com → 失败
    写完后执行测试。"
```

给 CC 一个对比标准，它就能自我检验，不用你逐行盯着看。这和 TDD 是互补的——TDD 适合核心逻辑，内置验证适合日常小任务。

### 5. 不是所有代码都值得你逐行审查

一个常见的误区：要么完全信任 CC 的输出（"跑通就行"），要么每行代码都自己盯着看。两种极端都不对——**代码越关键，你介入得越深；代码越边缘，你放手得越多。**

怎么判断该放手还是该盯？看一个标准：**这段代码出 bug 的代价有多大。**

| 代价等级 | 场景举例 | 你该怎么做 |
| ---- | ---- | ---- |
| 出 bug 无所谓 | 一次性数据迁移脚本、快速验证想法的原型 | **全权交给 CC**，跑通就行，代码质量不重要（这就是所谓的 vibe coding——只描述需求，不看中间过程） |
| 出 bug 要改 | 日常 CRUD、新增接口、页面样式调整 | **扫一眼结构和签名**，确认方向没跑偏 |
| 出 bug 要查 | 核心算法、状态机、复杂并发逻辑 | **逐行审查**，重点盯边界条件和异常路径 |
| 出 bug 要命 | 支付、权限校验、用户数据安全 | **你亲自写，让 CC 帮你审查**，主次别搞反了 |

![](images/Pasted%20image%2020260318092958.png)
像潜水——大部分时间浮在水面轻松前进，遇到关键水域再深潜检查。不用全程憋气，也不能全程只在水面漂。

**几个还挺常用的命令**

| 命令         | 用途             | 使用频率            |
| ---------- | -------------- | --------------- |
| `/clear`   | 清除对话，重新开始      | 高——每个新话题        |
| `/compact` | 压缩上下文          | 中——同一任务太长时      |
| `/context` | 查看当前上下文占用      | 中——感觉变慢时看一眼     |
| `/usage`   | 查看速率限制使用情况     | 低——想看还剩多少额度     |
| `/btw`     | 不打断主任务快速问一个侧问题 | 中——想问但不想丢失当前上下文 |

**搜索历史对话**
所有对话历史以 `.jsonl` 文件存储在 `~/.claude/projects/` 下。可以用 `grep -l -i "关键词" ~/.claude/projects/-Users-*/*.jsonl` 搜索，或者直接问 CC "我们之前讨论过关于 X 的什么？"

坦诚讲，这一点确实没有UI方便。

**输入框快捷键**：CC 的输入框不只是一个文本框，最有用的几个是
- `Ctrl+G` ：打开你的编辑器写 prompt，适合需要多行、粘贴代码片段、或者仔细组织语言的场景
- 双击`ESC` ：发出去的 prompt 不满意，可以立刻退回去改
- `Ctrl+V`：把剪切板里的图片给CC看

### 2. 别干等——Ctrl+B 后台运行

CC 执行耗时命令（`go test ./...`、`docker build`、`npm install`）时，你只能干等着，整个对话被卡住，什么都做不了。

**按 `Ctrl+B`，把正在执行的命令丢到后台。** CC 立刻恢复响应，你可以继续提问、讨论方案、甚至让它做别的事。命令跑完后会自动通知你结果。

子代理（Subagent）也一样——让一个子代理在后台扫代码库，你同时和主 CC 讨论设计方案，两边互不阻塞。

### 3 容器化运行高风险任务

如果你需要让 CC 做高风险操作（大规模重构、系统级变更），用 Docker 容器隔离：

```bash
# 在容器里运行 CC，容器内随便折腾，不影响宿主机
docker run -it --rm -v $(pwd):/workspace my-cc-sandbox-image
```

容器内可以用 `--dangerously-skip-permissions` 模式让 CC 全自动运行，因为即使出问题，影响范围限制在容器内，不至于CC 执行 `rm -rf` 丢失了整个 home 目录。容器化运行 + 定期审计批准的命令，是你的安全保障。

两个有用的工具：
- **`cc-safe`** 可以一键扫描你批准过的危险命令，`sudo`、`rm -rf`、`chmod 777`、`curl | sh`、`git reset --hard` 等危险模式，帮你发现潜在风险。
- **`SafeClaw`** 轻松创建和管理多个独立的 CC 容器实例。[SafeClaw](https://github.com/ykdojo/safeclaw)
