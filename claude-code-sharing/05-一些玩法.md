## 0. Git Worktree

在各类Agent使用的过程中，Git Worktree是比较多的应用工具。

我们比较习惯的同时处理多个分支的方式是：
`git stash` → `git checkout` → work work work → `git checkout`  → `git stash pop`。来回切换容易丢东西，而且同一时间只能在一个分支上工作。

Git Worktree 让你在**独立目录**里同时打开多个分支，每个目录跑一个 CC 实例，互不干扰，并行开发不切分支。

**基本操作**

```bash
# 当前在 main 分支
~/my-project/

# 创建 worktree：在新目录打开 feature/auth 分支
git worktree add ../my-project-feature1 feature/feature1
git worktree add ../my-project-feature2 feature/feature2
# 现在你有两个独立的工作目录
~/my-project-feature1/      ← feature/feature1 分支
~/my-project-feature2/      ← feature/feature2 分支
```

每个目录都是完整的工作空间，有自己的文件状态。你可以在每个目录里分别开一个 CC 实例。

worktree 的本质就是在磁盘上创建一个真实的目录，里面放的是同一个仓库的另一个分支的完整文件。

  ~/code/
  ├── my-project/           ← 主仓库（你当前所在）
  ├── my-project-auth/      ← worktree，检出 feature/auth 分支
  └── my-project-hotfix/    ← worktree，检出 hotfix 分支
  
**实战场景**

**场景一：功能开发 + 紧急修复并行**

```
Tab 1: ~/my-project-auth/     → CC 在开发新功能
Tab 2: ~/my-project-hotfix/   → CC 在修紧急 bug

两边互不干扰，不需要 stash，不需要切分支
```

**场景二：开发 + 审查并行**

```
Tab 1: ~/my-project-feature/  → CC 在写代码
Tab 2: ~/my-project-reviewer/          → 另一个 CC 审查 Tab 1 的代码

一个写，一个审，代码质量更高
```

**场景三：尝试性重构**

```bash
# 创建一个临时 worktree 试验重构方案
git worktree add ../my-project-refactor -b experiment/refactor

# 在 worktree 里让 CC 大胆重构，不影响主目录
# 满意 → 合并回来
# 不满意 → 直接删掉
git worktree remove ../my-project-refactor
```

**配合 Shell 别名**

> [!example]- Shell 别名 — worktree 快捷操作（点击展开）
> ```bash
> # ~/.zshrc
> alias wta='git worktree add'
> alias wtl='git worktree list'
> alias wtr='git worktree remove'
>
> # 快速创建 worktree 并进入
> wt() {
>   local name=$1
>   local branch=${2:-$1}
>   git worktree add "../$(basename $(pwd))-${name}" "$branch" && \
>   cd "../$(basename $(pwd))-${name}"
> }
>
> # 用法：wt auth feature/auth
> # 效果：创建 ../my-project-auth 并 cd 进去
> ```
> 👉 独立脚本：[cc-分享5-scripts/shell-aliases.sh](cc-%E5%88%86%E4%BA%AB5-scripts/shell-aliases.sh)

### 管理技巧

```
✅ 给 worktree 目录起有意义的名字（项目名-分支用途）
✅ 完成后及时清理：git worktree remove <path>
✅ 用 git worktree list 查看当前所有 worktree
❌ 不要在两个 worktree 里 checkout 同一个分支（git 不允许）
❌ 不要忘记清理，worktree 多了反而混乱
```

## 1.  Code Review

传统的CodeReview方式：打开 PR 页面，从上到下扫一遍 diff，看到哪算哪。文件多的时候很容易走马观花。

### 1.1 交互式审查

```
第一步：让 CC 拉取 PR 信息
你："review 一下这个 PR: https://github.com/xxx/yyy/pull/123"

CC 会用 gh 命令拉取 PR 的 diff、描述、评论，然后给你一个整体概览。
```

```
第二步：按层级深入
你："先看数据库相关的改动"
CC：（分析 migration 文件和 model 改动，指出潜在问题）

你："为什么这里用了 JSON 类型而不是独立的列？"
CC：（解释权衡，可能发现作者没考虑到的查询性能问题）

你："跑一下相关的测试"
CC：（执行测试，报告覆盖情况）
```

```
第三步：让 CC 直接留评论
你："把刚才发现的问题整理成 review 评论，提交到 PR 上"
CC：（用 gh api 在对应代码行留下评论）
```

### 1.2 推荐的审查顺序

不要从上到下看 diff，按**影响链路**审查更有效：

```
1. 协议/接口定义  → 契约对不对
2. 数据库变更      → migration 安全吗
3. 核心业务逻辑    → 功能正确吗
4. 错误处理        → 边界覆盖了吗
5. 测试            → 覆盖率够吗
```

每一层让 CC 聚焦分析，比一次性看完整个 diff 深入得多。

### 1.3 进阶：双 CC 实时协作——边写边审

不是写完再 review，而是**开发过程中实时审查**。一个 CC 写代码并定期提交，另一个 CC 自动检测到新提交、审查 diff、把反馈写回本地文件。开发 CC 在下一轮编码前读取反馈并修正。

**整体架构**

```
~/project-dev/            ← CC-Dev（开发者实例）
~/project-review/         ← CC-Reviewer（审查者实例）via worktree
.claude/reviews/          ← 共享邮箱（在主 worktree 目录下）
  ├── pending/            ← Dev 提交后自动写入审查请求
  │   └── a1b2c3.md
  └── done/               ← Reviewer 审查完写入反馈
      └── a1b2c3.md
```

**第一步：创建 Worktree**

```bash
# Reviewer 用 detached HEAD——不占用任何分支，只读 Dev 的提交
git worktree add ../project-review --detach
```

Reviewer 在独立目录工作，与 Dev 共享同一个 Git 数据库。Dev 的每一次 commit，Reviewer 通过 `git log feature/auth` 立刻可见。

**第二步：给 CC-Dev 配 Hook——提交后自动创建审查请求**

把检测逻辑放到脚本文件，避免 JSON 里写长命令：

脚本做了两件事：
1. **commit 后**：自动创建审查请求到 `pending/`
2. **每次 Bash 命令后**：检查 `done/` 有无新反馈，有就打印到 stdout → CC-Dev 自动看到

用 `.notified` 文件追踪已通知的反馈，每条反馈只打印一次，不重复。

> [!example]- `.claude/hooks/dev-hook.sh` — commit 后自动创建审查请求 + 检查反馈（点击展开）
> ```bash
> #!/bin/bash
> # CC Hook 通过 stdin 接收 JSON，不是环境变量
> INPUT=$(cat)
> COMMAND=$(echo "$INPUT" | jq -r '.tool_input.command // ""')
>
> # === Part 1: commit 后自动创建审查请求 ===
> if echo "$COMMAND" | grep -q "git commit"; then
>   HASH=$(git rev-parse --short HEAD 2>/dev/null)
>   if [ -n "$HASH" ]; then
>     PENDING=".claude/reviews/pending"
>     if [ ! -f "$PENDING/$HASH.md" ]; then
>       mkdir -p "$PENDING"
>       cat > "$PENDING/$HASH.md" << EOF
> commit: $HASH
> time: $(date '+%Y-%m-%d %H:%M')
> branch: $(git branch --show-current)
> ---
> $(git log -1 --format='%s%n%n%b')
> EOF
>     fi
>   fi
> fi
>
> # === Part 2: 检查是否有新的审查反馈 ===
> DONE=".claude/reviews/done"
> NOTIFIED=".claude/reviews/.notified"
> [ -d "$DONE" ] || exit 0
> touch "$NOTIFIED" 2>/dev/null
>
> for f in "$DONE"/*.md; do
>   [ -f "$f" ] || continue
>   NAME=$(basename "$f")
>   grep -qF "$NAME" "$NOTIFIED" 2>/dev/null && continue
>   echo ""
>   echo "=========================================="
>   echo "📬 收到新的审查反馈: $NAME"
>   echo "=========================================="
>   cat "$f"
>   echo ""
>   echo "$NAME" >> "$NOTIFIED"
> done
> ```
> 👉 独立脚本：[cc-分享5-scripts/dev-hook.sh](cc-%E5%88%86%E4%BA%AB5-scripts/dev-hook.sh)

> 注意：Hook 脚本依赖 `jq` 解析 JSON。安装：`brew install jq`

两个 Hook 各管一件事：
- **SessionStart**：CC-Dev 启动时自动显示未读反馈
- **PostToolUse**：每次 Bash 命令后触发 dev-hook.sh（创建审查请求 + 检查新反馈）

> [!example]- `.claude/settings.json`（项目级）— Hook 配置（点击展开）
> ```json
> {
>   "hooks": {
>     "SessionStart": [
>       {
>         "hooks": [
>           {
>             "type": "command",
>             "command": "DONE=.claude/reviews/done; COUNT=$(ls $DONE/*.md 2>/dev/null | wc -l | tr -d ' '); [ \"$COUNT\" -gt 0 ] && echo \"有 $COUNT 条未读审查反馈：\" && ls $DONE/*.md | while read f; do echo \"---\"; cat \"$f\"; done || echo '无待处理审查反馈'"
>           }
>         ]
>       }
>     ],
>     "PostToolUse": [
>       {
>         "matcher": "Bash",
>         "hooks": [
>           {
>             "type": "command",
>             "command": "bash .claude/hooks/dev-hook.sh"
>           }
>         ]
>       }
>     ]
>   }
> }
> ```
> 👉 独立配置：[cc-分享5-scripts/settings-dev-review.json](cc-%E5%88%86%E4%BA%AB5-scripts/settings-dev-review.json)

**第三步：用 CLAUDE.md 定义角色**

传统做法：每次启动 Reviewer 都手动贴一段角色 prompt。
更好的做法：把角色定义写进 CLAUDE.md，启动即自动加载。

两个 CC 启动时各自读自己的 CLAUDE.md，立刻知道自己的角色和规则。零手动。

> [!example]- Dev 项目根目录 `CLAUDE.md` — 开发者角色定义（点击展开）
> ```markdown
> ## Coding Guide
> 每完成一个独立的逻辑单元（一个函数、一个接口、一个 bug 修复），
> 立即 git add + git commit，不要攒着一起提交。
>
> ## Review Feedback
> 每次 git commit 后、开始下一个任务前，
> 先检查 .claude/reviews/done/ 有无新的审查反馈。
> 如果有，先阅读反馈并修改代码，再继续新任务。
> ```
> 👉 独立文件：[cc-分享5-scripts/CLAUDE-dev.md](cc-%E5%88%86%E4%BA%AB5-scripts/CLAUDE-dev.md)

> [!example]- Reviewer worktree 目录 `CLAUDE.md` — 审查员角色定义（点击展开）
> ```markdown
> # Code Reviewer
>
> 你是代码审查员。你的工作循环：
>
> 1. 检查 ~/project/.claude/reviews/pending/ 是否有新的 .md 文件
> 2. 如果有：
>    - 读取请求，获取 commit hash
>    - 执行 git log -p {hash} -1 查看完整 diff
>    - 审查代码（安全、性能、错误处理、可维护性）
>    - 将审查结果写入 ~/project/.claude/reviews/done/{hash}.md
>    - 删除 pending 中对应的请求文件
> 3. 如果没有，报告：当前无待审查提交
>
> 审查结果格式：CRITICAL / WARNING / SUGGEST / LGTM
>
> 启动后立即执行第一次检查。
> ```
> 👉 独立文件：[cc-分享5-scripts/CLAUDE-reviewer.md](cc-%E5%88%86%E4%BA%AB5-scripts/CLAUDE-reviewer.md)


之前还需要手动让 CC-Dev 检查反馈。现在有三层保障，完全不需要人介入：

1. **CLAUDE.md 规则**：告诉 Dev "commit 后先检查反馈再继续"
2. **Hook Part 2**：Dev 执行任何 Bash 命令时，自动扫描 `done/` 并把新反馈打印到 stdout——CC-Dev 在工具输出中直接看到
3. **SessionStart Hook**：新会话启动时，自动显示所有未读反馈

**运转流程**

```
CC-Dev (Terminal 1)                              CC-Reviewer (Terminal 2)

启动 → 读 CLAUDE.md                              启动 → 读 CLAUDE.md
  → 知道"小步提交"规则                              → 知道自己是审查员
  → SessionStart Hook 显示未读反馈                   → /loop 30s 开始轮询
   │
   ▼
1. 收到开发任务，开始写代码
   │
   ▼
2. 写完一个函数
   │ CLAUDE.md 规则驱动：
   │ "完成一个逻辑单元就提交"
   ▼
3. git add + git commit
   │
   ▼
4. PostToolUse Hook Part 1 触发
   → 自动创建 pending/a1b2c3.md
   │
   │                                        5. /loop 检测到 pending/a1b2c3.md
   │                                           → git log -p a1b2c3 -1 读 diff
   │                                           → 审查代码
   │                                           → 写入 done/a1b2c3.md
   │                                           → 删除 pending/a1b2c3.md
   │
6. Dev 继续写下一个函数
   期间执行 Bash 命令（go build、ls ...）
   │
   ▼
7. PostToolUse Hook Part 2 触发
   → 扫描 done/ 发现 a1b2c3.md
   → 反馈内容打印到 stdout
   → CC-Dev 在工具输出中自动看到
   │
   ▼
8. CC-Dev 根据反馈修改代码
   │
   ▼
9. 修完 → git commit（CLAUDE.md 驱动）
   │
   ▼
10. Hook Part 1 再次创建 pending/b2c3d4.md
    │
    │                                       11. Reviewer 检测 → 审查 → 写反馈 → ...
    ▼
   循环继续...
```

**全链路零手动**：

| 环节     | 驱动方                     | 人需要做什么  |
| ------ | ----------------------- | ------- |
| 小步提交   | CLAUDE.md 规则            | 无       |
| 创建审查请求 | PostToolUse Hook Part 1 | 无       |
| 轮询审查   | /loop 30s               | 启动时敲一次  |
| 反馈回流   | PostToolUse Hook Part 2 | 无       |
| 修改代码   | CC-Dev 自动响应             | 看一眼是否合理 |

**启动方式**：

```bash
# Terminal 1：Dev（不用贴任何 prompt）
cd ~/project-dev && claude
# → 直接说你要开发什么

# Terminal 2：Reviewer（不用贴任何 prompt）
cd ~/project-review && claude
# → 说 "开始检查" 或 /loop 30s
```

**这个方案优点**：
- **上下文隔离**——两个 CC 各自独立，Dev 读了 50 个文件不会污染 Reviewer 的上下文
- **异步协作**——Dev 不用等 review 完才能继续写，各干各的
- **全程自动**——Hook 触发、邮箱传递、反馈回流，人只需要在关键节点介入
- **用的都是现有能力**——Worktree + Hook + 文件 I/O + CLAUDE.md，没有魔法

**实用 prompt 模板**

```
# 快速审查
"review PR #123，重点关注安全和性能问题"

# 深度审查
"review PR #123，按以下顺序：
 1. 先看接口变更，判断是否向后兼容
 2. 再看核心逻辑，检查边界条件
 3. 最后看测试覆盖，指出遗漏的场景"

# 特定关注
"这个 PR 改了鉴权逻辑，帮我检查有没有权限绕过的风险"

# 循环审查（hard-review 命令）
"Repeat until no issues found:
 1. Review changed files
 2. Fix problems
 3. Review again
 Focus on: type consistency, edge cases, security, performance"
```

## 2. 搭配Custom Hooks

Hooks 是在 CC 执行特定操作时自动触发的脚本。和 CLAUDE.md 里写"请遵守 xxx 规则"不同，Hooks 是**确定性的**——不管 Claude 记不记得，Hook 都会执行。

### Hook 类型

CC 支持四种 Hook 触发时机：

| 触发时机 | 说明 | 典型用途 |
|---------|------|---------|
| `PreToolUse` | 工具调用前 | 阻断危险操作 |
| `PostToolUse` | 工具调用后 | 自动格式化、校验 |
| `Notification` | CC 发通知时 | 推送到飞书/企微 |
| `SessionStart` | 会话启动时 | 注入动态上下文 |

### 配置位置

```
~/.claude/settings.json              # 全局 hooks（所有项目生效）
<project>/.claude/settings.json      # 项目级 hooks
```

### 实战配方

**配方一：Edit 后自动格式化 Go 代码**

CC 每次用 Edit 工具修改 `.go` 文件后，自动跑 `gofmt`。不需要提醒 Claude "记得格式化"——它改完就自动格式化了。

> Hook 的工具信息通过 **stdin JSON** 传入，不是环境变量。用 `jq` 解析 `.tool_input.file_path` 获取文件路径。

> [!example]- Hook 配置 — Go 自动格式化（点击展开）
> ```json
> {
>   "hooks": {
>     "PostToolUse": [
>       {
>         "matcher": "Edit",
>         "hooks": [
>           {
>             "type": "command",
>             "command": "FILE=$(cat | jq -r '.tool_input.file_path // \"\"'); [ -n \"$FILE\" ] && [[ \"$FILE\" == *.go ]] && gofmt -w \"$FILE\" || true"
>           }
>         ]
>       }
>     ]
>   }
> }
> ```
> 👉 独立配置：[cc-分享5-scripts/hook-go-format.json](cc-%E5%88%86%E4%BA%AB5-scripts/hook-go-format.json)

**配方二：阻断修改受保护文件**

CC 试图修改 `migrations/` 或 `auth/middleware` 下的文件时，直接阻断。不靠 Claude 记住"这个目录不能改"，而是物理拦截。

> [!example]- Hook 配置 — 受保护文件阻断（点击展开）
> ```json
> {
>   "hooks": {
>     "PreToolUse": [
>       {
>         "matcher": "Edit|Write",
>         "hooks": [
>           {
>             "type": "command",
>             "command": "FILE=$(cat | jq -r '.tool_input.file_path // \"\"'); echo \"$FILE\" | grep -qE '(migrations/|auth/middleware)' && echo 'BLOCKED: 受保护文件，请先获得审批' && exit 1 || exit 0"
>           }
>         ]
>       }
>     ]
>   }
> }
> ```
> 👉 独立配置：[cc-分享5-scripts/hook-protect-files.json](cc-%E5%88%86%E4%BA%AB5-scripts/hook-protect-files.json)

**配方三：SessionStart 注入动态上下文**

每次启动 CC 会话，自动注入当前 Git 状态。CC 一开始就知道你在哪个分支、最近改了什么。

> [!example]- Hook 配置 — 会话启动注入 Git 状态（点击展开）
> ```json
> {
>   "hooks": {
>     "SessionStart": [
>       {
>         "hooks": [
>           {
>             "type": "command",
>             "command": "echo \"当前分支: $(git branch --show-current)\n最近提交: $(git log --oneline -3)\n未提交变更: $(git status --short)\""
>           }
>         ]
>       }
>     ]
>   }
> }
> ```
> 👉 独立配置：[cc-分享5-scripts/hook-session-context.json](cc-%E5%88%86%E4%BA%AB5-scripts/hook-session-context.json)

**配方四：任务完成后推送通知**

CC 后台跑长任务时，完成后弹出系统通知。可以替换成飞书/企微 webhook 推送。

> [!example]- Hook 配置 — 任务完成系统通知（点击展开）
> ```json
> {
>   "hooks": {
>     "Notification": [
>       {
>         "hooks": [
>           {
>             "type": "command",
>             "command": "MSG=$(cat | jq -r '.notification // \"Task completed\"'); osascript -e \"display notification \\\"$MSG\\\" with title \\\"Claude Code\\\"\""
>           }
>         ]
>       }
>     ]
>   }
> }
> ```
> 👉 独立配置：[cc-分享5-scripts/hook-notification.json](cc-%E5%88%86%E4%BA%AB5-scripts/hook-notification.json)

### 设计原则

```
✅ 适合 Hook 的：格式化、lint、阻断、通知——简单、快速、确定性
❌ 不适合 Hook 的：复杂语义判断、长时间运行、需要多步推理
```

Hook 跑太慢会阻塞 CC 循环。保持每个 Hook 在 1-2 秒内完成。注意限制输出长度（`| head -30`），避免 Hook 输出反而污染上下文。

## 3. 固化业务Custom Skill

如果你发现自己在 CC 里重复做同一件事超过两次，就该把它封装成 Skill。

Skill 本质是一份保存好的工作流。你定义好步骤，取个名字，以后只需要调用名字（`/my-skill`）或者让 CC 自动识别触发。

### Skill 文件结构

```
.claude/skills/
└── code-review.md        # 一个 Skill = 一个 markdown 文件
```

> [!example]- Skill 示例 — Go 代码审查（点击展开）
> ```markdown
> ---
> name: code-review
> description: Review Go code for idiomatic patterns, concurrency safety,
>   error handling, and performance. Use when reviewing Go source files or PRs.
> ---
>
> ## 审查步骤
>
> 1. 检查错误处理：是否每个 error 都被处理，不要 `_ = err`
> 2. 检查并发安全：goroutine 中访问共享变量是否有锁/channel 保护
> 3. 检查资源释放：defer close、context cancel
> 4. 检查命名规范：exported 函数有注释，变量名符合 Go 惯例
> 5. 检查测试覆盖：关键路径是否有测试
>
> ## 输出格式
>
> 按严重程度分类：
> - 🔴 CRITICAL：必须修复
> - 🟡 WARNING：建议修复
> - 🟢 SUGGESTION：可以改进
> ```
> 👉 独立文件：[cc-分享5-scripts/skill-code-review.md](cc-%E5%88%86%E4%BA%AB5-scripts/skill-code-review.md)

### 从重复操作到 Skill 的过程

**第一步：发现重复**

你发现自己每次做代码审查都在说同样的话：

```
"帮我 review 这段代码，重点看错误处理、并发安全、资源释放"
```

**第二步：提取为 Skill**

把重复的 prompt 整理成结构化的 SKILL.md，加上 frontmatter。

**第三步：调试触发精度**

description 写得太短（`help with code`）会误触发，写得太长又占上下文。关键是写清楚 **"什么时候该用我"**，而不是"我能做什么"。

```yaml
# ❌ 太宽泛：任何代码相关的问题都可能触发
description: help with code review

# ✅ 精确：只在审查 Go 代码时触发
description: Review Go code for idiomatic patterns, concurrency safety,
  error handling, and performance. Use when reviewing Go source files or PRs.
```

**第四步：拆分大 Skill**

一个 Skill 只做一件事。不要把 review + deploy + debug 塞进同一个 Skill——你只想 review 时，deploy 和 debug 的内容也会被注入上下文，浪费 token。

**supporting files**

Skill 正文不要超过 200 行。大量参考资料放到 supporting files：

```
.claude/skills/
├── code-review.md           # 主文件：步骤 + 触发条件
└── code-review/
    ├── go-pitfalls.md       # 支撑文件：Go 常见陷阱清单
    └── security-checklist.md # 支撑文件：安全检查项
```

主文件里引用：

```markdown
详细的 Go 陷阱清单见 `code-review/go-pitfalls.md`
```

CC 需要时会自己去读 supporting files，不会一次性全部加载。

**手动触发 vs 自动触发**

```yaml
# 读操作（分析、review）→ 允许自动触发，没风险
description: Review Go code for...

# 写操作（部署、删除、发消息）→ 必须手动触发
# 在 SKILL.md 的 frontmatter 中设置：
disable-model-invocation: true
# 只能通过 /deploy 手动触发，CC 不会自作主张
```

**规则**：读操作让 CC 自动调用没问题；有副作用的操作必须手动触发。

### 更多 Skill 灵感——CC 团队的真实实践

CC 创始人 Boris Cherny 分享了团队内部的几个 Skill 案例，可以作为灵感：

- **`/techdebt` 命令**：每次会话结束时运行，查找并消除重复代码——技术债务不积累
- **上下文同步 Skill**：一个斜杠命令同步 7 天的 Slack、GDrive、Asana 和 GitHub 到一个上下文转储——开会前跑一遍，快速了解项目进展
- **BigQuery 分析 Skill**：团队提交到代码库中，所有人直接在 CC 中做分析查询——Boris 说他已经 6 个月没写过一行 SQL 了
- **analytics-engineer 风格 Agent**：编写 dbt 模型、审查代码、在 dev 环境测试变更

### 一个案例：AIK弹窗业务skill

AIK弹窗业务模式比较固定，弹窗通道拉取各个业务方的弹窗接口数据，并根据优先级和频控来决策是否要下发弹窗，把这个业务固化为skill:

1. Phase 1：交互式信息收集，依次收集：英文名称 → 中文描述 → 弹窗模式 → 业务 API → Service Key 设计 → Params 配置 → 频控方案 → 前置过滤器 → 优先级 → 确认总览
2. Phase 2：Protocol 修改：在kugou-protocol仓库的enum ServiceType中添加新枚举值，提交并等待流水线生成代码（1-2分钟）
3. Phase 3：代码生成
	1. 生成popup/service/windower/{name}.go（Windower 实现，含 Attribute/New/PreFilter/Invoke/PostFilter/Notify） 
	2. 更新popup/service/init.go（按优先级位置注册） 
	3. 可选：生成 Apollo 开关配置、业务侧集成代
4. Phase 4：依赖更新：go get -u更新协议依赖 → go mod tidy → go build 编译验证
5. Phase 5：验证与文档：生成验证 Checklist 和使用指南文档，覆盖 Protocol、代码、功能、集成、数据库、测试等维度

附加价值：skill 还内置了8 个常见问题的排查指南：（ServiceType 找不到、弹窗不显示、频控不生效、优先级异常等），方便开发和调试。

自定义命令的核心价值是将团队的最佳实践固化为可重复执行的工作流。

## 4. Agent Teams

> 这是 CC 目前最前沿的能力。如果前面四个是"单人作战"的增强，这个是"组建团队"。

Agent Teams 让你同时运行多个持久的 Claude 实例，各自有独立身份和上下文，通过文件系统邮箱通信。

和 Subagent 的区别：

| | Subagent | Agent Teams |
|---|---------|-------------|
| 生命周期 | 一次性：生成→执行→返回→消亡 | 持久：保持运行，等待任务 |
| 身份 | 无 | 有名字、有角色 |
| 通信 | 无（只返回结果给主会话） | 有（文件邮箱，agent 之间可互发消息） |
| 适用场景 | 单次调研、扫码库 | 持续协作、多角色分工 |

### 团队结构

```
.team/
  config.json           # 团队名册 + 角色定义
  inbox/
    leader.jsonl        # Leader 的收件箱
    coder.jsonl         # Coder 的收件箱
    reviewer.jsonl      # Reviewer 的收件箱
```

### 实战场景：开发 + 审查 + 测试三角

```
Leader（你 + 主 CC）
  │
  ├── 分配任务 ──→ Coder（写代码）
  │                   │
  │                   └── 写完通知 ──→ Reviewer（审查代码）
  │                                      │
  │                                      └── 审查结果 ──→ Leader
  │
  └── 根据审查结果决定：合并 / 要求修改
```

每个 Agent 在自己的上下文窗口里工作，互不污染。Coder 读了 50 个文件不会占用 Reviewer 的上下文。

### 协作协议

**计划审批**：高风险操作前需要 Leader 确认

```
Coder 发现需要修改数据库 migration
  → 发消息给 Leader："我需要修改 migration 文件，方案是 xxx，请审批"
  → Leader 审查后回复 approve / reject
  → Coder 根据回复行动
```

**优雅关机**：不能直接杀线程

```
Leader 发送 shutdown 请求
  → Agent 完成当前工作
  → 保存进度
  → 清理资源
  → 确认关机
```

### 自主 Agent：不用手动分配

更进一步，Agent 可以自己认领任务：

```
.tasks/
├── task_1.json    # status: pending    → 未认领
├── task_2.json    # status: in_progress → 已被 Coder 认领
└── task_3.json    # status: completed   → 已完成
```

Agent 的工作循环：

```
工作 → 完成 → 检查收件箱 → 没消息 → 扫描任务板 → 有未认领的任务 → 认领 → 工作
                                                → 没任务 → 等待 5 秒 → 再检查
                                                → 60 秒无活动 → 自动关机
```

核心突破：**Agent 自己看板，有活就认领**——不需要 Leader 逐个分配。

### 配合 Worktree：终极形态

每个 Agent 在自己的 Git Worktree 里工作：

```
控制平面 (.tasks/)              执行平面 (.worktrees/)
├─ task_1.json  ←────────→  auth-refactor/     ← Agent A 在这里工作
├─ task_2.json  ←────────→  ui-login/          ← Agent B 在这里工作
└─ task_3.json               （待认领）
```

文件系统隔离 + Git 隔离，两个 Agent 同时改代码也不会互相污染。

### 崩溃恢复与成本感知

**崩溃恢复**：如果进程意外中断，CC 不会自动重启 Teammate——这是刻意的安全设计，防止失控 Agent 持续烧 token。重启后 busy 成员会被强制转为 ready，由 Lead 重新分配任务。

**成本感知**：

| 配置 | 约消耗 Token |
|------|-------------|
| 单 Agent | ~200K（一个 context window） |
| 3 Agent Team | ~800K（Lead + 3 × ~200K） |
| 每个 Teammate 启动开销 | ~50-80K（CLAUDE.md + MCP + skills） |

Anthropic 用 16 个 Agent 构建 C 编译器，产出 100K 行 Rust 代码，编译 Linux 6.9 内核，总成本约 $20,000。

**建议**：团队规模控制在 3-5 人，每人 5-6 个任务。不要一开始就上大规模 Agent Teams——先用 Subagent 和 Worktree 解决 80% 的并行需求，真正需要持久协作时再上 Teams。

## 5. Claude Code SDK

CC 不只能手动使用，它还提供编程接口（SDK），可以作为组件嵌入到更大的自动化系统中：

```javascript
import { query } from "@anthropic-ai/claude-code-sdk";

for await (const message of query({
  prompt: "分析这个项目的测试覆盖率",
  options: { mcpServers: { /* ... */ } }
})) {
  if (message.type === "result") console.log(message.result);
}
```

适合批量处理任务、CI/CD 集成、构建自定义工具链。
