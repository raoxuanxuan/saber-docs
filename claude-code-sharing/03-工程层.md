## 1. ClAUDE.md

大多数人把 CLAUDE.md 当成一个 prompt 文件来用——写几行指令，期望 CC 记住。但 Claude 要像一个项目原生工程师一样工作，它始终需要四样东西：

- **the why** → 这个系统做什么、为什么存在
- **the map** → 代码在哪里、怎么组织的
- **the rules** → 什么允许、什么不允许
- **the workflows** → 工作怎么做、流程是什么

一个 CLAUDE.md 文件塞不下这四样。所以需要把它们分散到项目结构的不同位置，各司其职：

```
your-repo/
├── CLAUDE.md                    # 北极星：目的 + 地图 + 规则
├── .claude/
│   ├── skills/                  # 可复用专家模式
│   │   ├── code-review.md
│   │   ├── refactor.md
│   │   └── release.md
│   └── settings.json            # hooks 配置（确定性护栏）
├── docs/                        # 渐进式上下文
│   ├── architecture.md
│   ├── adr/                     # 架构决策记录
│   └── runbooks/                # 运维手册
├── src/
│   ├── auth/
│   │   └── CLAUDE.md            # 分层设
│   ├── persistence/
│   │   └── CLAUDE.md
│   └── ...
└── infra/
    └── CLAUDE.md                # 基础设施注意事项
```

**核心观点：Prompting 是临时的，Structure 是永久的。** 当你的仓库按这种方式组织时，CC 不再像一个聊天机器人，而是开始像一个住在你仓库里的工程师——进入任何目录，都能自动读到该知道的东西。

原则：**始终常驻的放 CLAUDE.md，按需加载的放 docs/，确定性的放 Hooks。**

**分层管理**——对于大型项目，CLAUDE.md 不是只有一个：

```
~/.claude/CLAUDE.md          # 全局：个人偏好、通用规范（所有项目生效）
rms/CLAUDE.md                # 项目级：共享数据库、服务架构
rms/aik_song/CLAUDE.md       # 服务级：具体业务逻辑、接口规范
```

层级越深，内容越具体。Claude 会同时读取所有层级——全局的"用 Go 写代码"不需要在每个项目里重复写。

**维护策略**：

- **踩坑后**：将 bug 根因和解决方案记录为规范
- **架构决策后**：记录"为什么这样设计"而不只是"是什么"
- **发现自己重复口头告诉 CC 同一件事**：写进 CLAUDE.md
- **保持简洁**：Anthropic 官方自己的 CLAUDE.md 只有约 2.5K tokens

**docs/**

CLAUDE.md 应该短小精悍，那架构文档、设计决策这些长内容放哪？答案是 `docs/` 目录，CC 不需要一开始就知道所有细节，不要撑爆了上下文，CC只需要知道**详情在哪里**：

```
docs/
├── architecture.md          # 系统架构概览
├── adr/                     # 架构决策记录（为什么选 gRPC 不选 REST）
│   ├── 001-grpc-over-rest.md
│   └── 002-event-driven-sync.md
└── runbooks/                # 运维手册（如何部署、如何排障）
    ├── deploy.md
    └── incident-response.md
```

在 CLAUDE.md 里只需要写一行指引：

```
架构文档在 docs/ 目录，修改核心模块前先阅读 docs/architecture.md
```

CC 需要时会自己去读。这就是"渐进式上下文"——按需加载，不预先占用宝贵的上下文窗口。

## 2. Skill

> Skill 不是模板库，是用的时候才加载的工作流。

### 好 Skill 的标准

- 描述要让模型知道"**何时该用我**"，而不是"我是干什么的"（这两个差很多）
- 有完整步骤、输入、输出和停止条件
- 正文只放导航和核心约束，大资料拆到 supporting files 里
- 有副作用的 Skill 要显式设置 `disable-model-invocation: true`

### Skill 的结构（Progressive Disclosure）

- **SKILL.md** — 定义任务语义、边界和执行骨架
- **supporting files** — 提供领域细节
- **脚本** — 确定性收集上下文或证据

可用 `skill-creator` 创建。

### Skill 的类型

| 类型          | 用途                | 示例         | 设计要点               |
| ----------- | ----------------- | ---------- | ------------------ |
| 检查清单型（质量门禁） | 发布前跑一遍，确保不漏项      | 安全检查、发布清单  | 每项可独立判断，支持部分通过     |
| 工作流型（标准化操作） | 高风险操作，显式调用 + 内置回滚 | 配置迁移、数据库变更 | 步骤有序、有回滚方案、必须手动触发  |
| 领域专家型（决策框架） | 按固定路径收集证据，不要瞎猜    | 运行时排障、性能分析 | 先收集数据再下结论，避免模型凭直觉猜 |
### 常见的坑

**1. 描述过短 → 误触发**

```yaml
# 反模式
description: help with backend
# 问题：太宽泛，问个 Go 语法问题也可能触发

# 正模式
description: Design REST API endpoints with pagination, filtering, error responses, and rate limiting for production Node.js services.
```

**2. 正文过长 → 浪费上下文**

反模式：SKILL.md 正文 500 行工作手册。被调用后注入当前会话，500 行 ≈ 2000-3000 tokens，持续占用直到被 compaction 压缩。

**3. 一个 skill 覆盖太多职责 → 既浪费又模糊**

- 你只想 review 代码，但 deploy/debug/docs/incident 的内容也全部注入了
- description 必然写得很宽泛（回到反模式 1）
- CC 无法精准判断什么时候该调用

正模式：拆成独立 skill，各司其职。

**4. 有副作用的 skill 允许自动调用 → 危险**

```yaml
# 反模式
description: Deploy to production when code is ready
# CC 判断"代码准备好了"就自动触发 → 意外部署

# 反模式
description: Clean up stale branches and unused resources
# CC 觉得"该清理了"就自动触发 → 意外删除

# 正模式：有副作用的 skill 只允许手动 /deploy 触发
```

> **原则**：读操作（分析、review）让 CC 自动调用没问题；写操作（部署、删除、发消息）必须手动触发。

### Skill 设计总结

`description` 控制触发精度，正文控制上下文开销，职责控制两者的乘积，副作用控制风险边界。设计不好的 skill 会同时浪费上下文、频繁误触发、还可能搞出危险操作。

## 3. Tool

![](images/Pasted%20image%2020260313174603.png)

给 agent 用的工具，重点不是功能堆得多完整，而是让它更容易用对：

- 名称前缀按系统或资源分层：`github_pr_*`、`jira_issue_*`
- 对大响应支持 `response_format: concise / detailed`
- 错误响应要教模型如何修正，不要只抛 opaque error code
- 能合并成高层任务工具时，不要暴露过多底层碎片工具，避免 `list_all_*` 让模型自行筛选

## 4. Hooks

> Hooks 不是"自动运行的脚本"，而是把不能交给 Claude 临场发挥的事情收回到确定性流程里。

格式化要不要跑、保护文件能不能改、任务完成后要不要通知——这些事真不要指望 Claude 每次都自己记得。

**适合的场景：**
- 阻断修改受保护文件
- Edit 后自动格式化 / lint / 轻量校验
- SessionStart 后注入动态上下文（Git 分支、环境变量）
- 任务完成后推送通知

**不适合的场景：**
- 需要读大量上下文的复杂语义判断
- 长时间运行的业务流程
- 需要多步推理和权衡的决策（这些该在 Skill 或 Subagent 里）

**关键机制**：Hook 脚本返回退出码 `2` 会**阻止执行**，并将错误信息反馈给 Claude。这是实现"物理拦截"而非"口头约束"的核心。


![](images/Pasted%20image%2020260313175008.png)

一些常用的Hook:

| 事件                  | 触发时机          | 典型用例                 |
| ------------------- | ------------- | -------------------- |
| `PreToolUse`        | 工具执行前         | 阻止修改受保护文件            |
| `PostToolUse`       | 工具执行后         | 自动格式化、lint 校验        |
| `SessionStart`      | 会话开始时         | 注入动态上下文（Git 分支、环境变量） |
| `Notification`      | CC 发通知时       | 推送到飞书/企微             |
| `UserPromptSubmit`  | 用户提交 prompt 时 | 验证输入、注入上下文           |
| `PermissionRequest` | 权限对话框出现时      | 自动批准安全操作             |
| `Stop`              | 响应完成后         | 回合结束质量检查             |

### 三层叠加：Hooks + Skills + CLAUDE.md

| 层 | 职责 |
|----|------|
| **CLAUDE.md** | 声明"提交前必须通过测试和 lint" |
| **Skill** | 告诉 Claude 在什么顺序下运行测试、如何看失败、如何修复 |
| **Hook** | 对关键路径执行硬性校验，必要时阻断 |

三样少任何一层都会有漏洞。只写 CLAUDE.md 规则，Claude 经常当没看见；只靠 Hooks，细节判断又做不了，放在一起才比较稳。

### 插件中的 Hooks

在 `settings.json` 中启用插件后：

```json
"enabledPlugins": {
    "superpowers@superpowers-dev": true
}
```

加载链路：

```
settings.json 的 enabledPlugins
  → 找到 superpowers@superpowers-dev
  → 定位到 ~/.claude/plugins/cache/superpowers-dev/superpowers/4.1.1/
  → 读取该目录下的 hooks/hooks.json
  → 注册里面定义的所有 hooks
```

插件是一个自包含的包，内部可以带自己的 hooks、skills、agents。CC 启动时扫描所有 enabledPlugins，自动加载每个插件目录下的 `hooks/hooks.json`。这就是为什么这些 hook 在 `/hooks` 界面里显示为 `[Plugin Hook] (read-only)` — 它们由插件系统单独管理，不在 `settings.json` 的 hooks 字段里。

## 5. SubAgent

Subagent 就是从主对话派出去的一个独立 Claude 实例。有自己的上下文窗口、只用你指定的工具、干完汇报结果。

**核心价值不是"并行"，而是隔离**：扫代码库、跑测试、做审查这类会产生大量输出的事，交给 Subagent 做，主线程只拿摘要，不会被中间过程污染。

![](images/Pasted%20image%2020260313175719.png)

本质上自定义 agent 就是在内置 general-purpose 的基础上加了**角色限定 + 工具限定 + 模型限定**。

> 成本差距：Opus 大约是 Haiku 的 50-100 倍。让 Explore agent 跑 Opus 扫文件纯粹浪费钱。

### Agent 关键配置

**1. tools / disallowedTools — 最小权限原则**

```yaml
# 反模式：不限定工具，子进程能做任何事
tools: ["*"]

# 正模式：只给需要的工具
tools: ["Read", "Grep", "Glob", "Bash"]

# 或者用排除法
disallowedTools: ["Edit", "Write", "Bash"]
```

**2. model — 按任务匹配成本**

```yaml
model: haiku    # 扫库搜索，不需要强推理
model: sonnet   # 日常编码/review，平衡之选
model: opus     # 架构决策/复杂审查，需要深度推理
```

**3. maxTurns — 防止跑飞**

```yaml
# 简单 review agent，最多 10 轮就该出结果了
maxTurns: 10

# 不设的话，agent 可能无限循环：
# 读文件 → 发现依赖 → 读依赖 → 发现更多依赖 → ...
# 跑了 50 轮，烧了一堆 token，结果偏离主题
```

**4. isolation: worktree — 文件系统隔离**

```yaml
isolation: worktree
# CC 创建一个临时 git worktree（独立的工作目录副本）
# agent 在副本里随便改，不影响你当前的工作目录
# 改完后你可以选择性地合并回来
```

适用场景：让 agent 尝试一个重构方案，但你不确定要不要用——在 worktree 里试，不满意直接丢弃。

### 后台执行

长时间运行的 bash 命令可以按 `Ctrl+B` 移到后台，Claude 之后会用 BashOutput 工具查看结果，不会阻塞主线程。Subagent 同理，直接告诉它"在后台跑"就行。

```
默认行为：CC 调用 Bash → 等待 2 分钟 → 你和 CC 都干等着
按 Ctrl+B：CC 调用 Bash → 命令移到后台 → CC 继续和你对话 → 命令跑完后收到通知
```

### SubAgent 的隔离机制

在 Agent Teams 场景中，Teammate spawn 的 Subagent 不能访问 Team 工具。具体通过三层机制实现：

- **Permission Deny Rules**：Team 工具被显式 deny
- **Tool Visibility Hiding**：Team 消息工具从 Subagent 工具集中完全移除
- **Output Relay**：Subagent 结果返回给父 Teammate，由 Teammate 决定是否广播

这样防止 Subagent 直接发消息给其他 Teammate，造成通信混乱。


### SubAgent 要避免的问题

- 子代理权限和主线程一样宽，隔离没有意义
- 输出格式不固定，主线程拿到没法用
- 子任务之间强依赖，频繁要共享中间状态（这种情况不适合用 Subagent）

### 多 Agent 协作——从团队到自组织

> 这一部分是 CC 架构的前沿能力，从单 Agent 走向真正的多 Agent 系统。

Agent Teams 的所有能力都由 7 个 Tool Call 组合而成，构成了完整的"指令集"：

| 原语 | 功能 | 映射到磁盘操作 |
|------|------|----------------|
| `TeamCreate` | 创建团队目录和 config.json | `mkdir + write` |
| `Task(team_name)` | 以完整 CC 进程 spawn 一个 Teammate | `fork process` |
| `TaskCreate` | 创建任务 JSON 文件 | `write {id}.json` |
| `TaskList` | 扫描所有任务文件，返回状态 | `readdir + read` |
| `TaskUpdate` | 修改任务状态/owner（带文件锁） | `flock + write` |
| `SendMessage` | 向目标 agent 的 inbox 追加消息 | `append to inbox.json` |
| `TeamDelete` | 清理整个团队目录 | `rm -rf` |

所有复杂的多 Agent 协作行为，都可以分解为这些原语的组合。**没有数据库，没有消息队列，没有 gRPC——就是文件读写。**

### Agent Teams——持久身份 + 文件邮箱

s04 的 Subagent 是一次性的：生成 → 执行 → 返回摘要 → 消亡。没有持久身份，没有跨调用记忆。

真正的团队需要三样东西：持久 Agent、身份管理、Agent 间通信通道。

CC 的实现是**文件系统邮箱**：

```
.team/
  config.json           # 团队名册 + 状态
  inbox/
    alice.jsonl         # 仅追加，读后清空
    bob.jsonl
    lead.jsonl
```

通信流程：
- `send("alice", "bob", ...)` → 追加一行 JSON 到 `bob.jsonl`
- `read_inbox("bob")` → 读取全部消息后清空文件

每个队友在独立线程运行自己的 agent loop，通过 JSONL 文件异步通信，不共享上下文。

队友生命周期：`spawn → WORKING ↔ IDLE → SHUTDOWN`

### Team Protocols——优雅关机与计划审批

仅有消息传递还不够。两个关键场景需要结构化协议：

1. **关机协议**：直接杀线程会留下半写的文件和脏状态
2. **计划审批**：高风险操作前需要领导审批

两个协议用**同一套状态机**：

```
Leader 发送 request（带 request_id）
  → Teammate 收到，处理，回复 approve/reject（带同一 request_id）
  → FSM: [pending] → [approved] | [rejected]
```

shutdown 和 plan_approval 的区别只是消息类型不同，FSM 逻辑完全复用。

Autonomous Agents——自组织

前面的团队模式还是"领导指派"——Leader 必须为每个队友写 prompt。10 个未认领的任务需要手动分配，这扩展不了。

自主 Agent 的创新是**双阶段循环**：

```
WORK 阶段：标准 Agent 循环，执行工具调用
    ↓ stop_reason != tool_use
IDLE 阶段：每 5 秒轮询
    ├→ 检查 inbox → 有消息？ → 进入 WORK
    ├→ 扫描 .tasks/ → 有未认领任务？ → 自动认领 → 进入 WORK
    └→ 60 秒无活 → SHUTDOWN
```

核心突破：**"队友自己看看板，有活就认领"——无需领导逐个分配。**

**任务抢占的并发安全**：两个 Teammate 同时抢同一任务怎么办？CC 用 `flock` 文件锁保证原子性：

```
1. Teammate A 调用 TaskList()，返回 pending 且 owner 为空的任务
2. Teammate A 调用 TaskUpdate(claim)，获取 flock(.lock) 文件锁
3. 在锁保护下：读取任务文件，检查 owner 为空 → 设置 owner=A → 写回
4. 释放锁，返回成功
```

两个 Teammate 同时抢时，只有先拿到锁的能成功。优先级规则：**最小 ID 优先**。

还有一个精巧的细节——**身份重注入**：上下文压缩后 Agent 可能忘了自己是谁。解决方案是检测到 messages 过短（表示发生了压缩）时，在开头重新插入身份信息。
